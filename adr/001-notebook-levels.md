# ADR-001: Тетрадь из уровней L0–L3 с подъёмом факта кодом

| Код | `harness/notebook.py`, `harness/agent.py`, `harness/context.py` |

## Контекст

Система месяцами собирает и обновляет факты о ~150–200 стипендиях (дедлайны, суммы, условия) из разнородных официальных страниц и отвечает по ним пользователям. Требования, которые определяют выбор:

1. **Провенанс каждого факта** (M6 = 100 %): значение + URL + дата проверки + статус + дословная цитата, и цитата проверяема кодом (M8: «цитата есть в снимке страницы»).
2. **Противоречия не затираются** (M7: 0 тихих перезаписей): официальный источник против агрегатора, прошлый цикл против текущего, исправление пользователя.
3. **Исправление пользователя доходит до всех следующих ответов** (M9) и может быть отменено.
4. **Объём:** ~1,8M токенов снимков страниц к защите — примерно в 10 раз больше окна модели; на ответ — ≤16k входных токенов (3.1).
5. **Стоимость** ≤$8/мес: модель вызывается только когда страница реально изменилась.
6. **Воспроизводимость eval:** сайты меняются, метрики должны считаться на зафиксированных снимках.
7. **Статус цикла и даты — кодом, а не моделью** (по спайку модель ставит «подтверждён» без дат).

## Решение

Четыре уровня с однонаправленным подъёмом **L0 → L1 → L2 → L3**; вверх данные поднимает только код:

| Уровень | Что | Изменяемость | Попадает в промпт |
|---|---|---|---|
| L0 | снимок страницы: текст после trafilatura, sha256, дата загрузки | неизменяем, новая загрузка — новая строка | только при извлечении (одна страница) |
| L1 | атомарный факт: значение, цикл, область, источник, цитата, `checked_at`, статус жизни; журнал `l1_events` | не удаляется и не перезаписывается; меняется только статус (`retracted` / `quarantined` / `superseded`) с записью в журнал | для карточки в фокусе (источник, конфликт, исправление) |
| L2 | карточка стипендии: рабочее значение + статус + альтернативы | производная: всегда пересчитывается из активных фактов L1 по политике ADR-002 | до 8 карточек по retrieval |
| L3 | резюме: ближайшие дедлайны, «требует внимания» | производное от L2 | всегда, ≤3k |

Правила подъёма:
- **L0 → L1:** модель извлекает факты одной страницы по JSON-схеме; валидатор (код) пропускает факт, только если цитата буквально есть в снимке, формат даты соответствует точности, цикл корректен. Запись по стипендии атомарна;
- **L1 → L2:** политика противоречий — код (новый цикл > старый; официальный > пользователь > агрегатор > прошлогодний снимок; при конфликте официального и пользователя — более ранний дедлайн; любое расхождение → `конфликт`, все значения видны);
- **исправление пользователя** — обычный факт L1 с источником `user:<id>`: участвует в той же политике, отменяется сменой статуса;
- **перепроверка:** sha256 текста против L0; не изменилось → кэш извлечения, модель не вызывается.

## Отвергнутые варианты

### A. Все тексты в один промпт с усечением (long context, бывший baseline v0.1)
Каждый ответ: релевантные страницы целиком в окно модели, модель сама отвечает и разрешает противоречия.

**Почему отказались:** база в ~10 раз больше окна → усечение молча выбрасывает страницы, и нельзя сказать, какой факт потерян; противоречия разрешает модель внутри одного вызова — без следа и с риском «тихо» выбрать агрегатор (M7); цитаты не проверяются кодом против неизменяемого снимка; каждый ответ стоит ~100k+ токенов вместо ~12k — в 8–10 раз дороже U4 и выходит за $8/мес; исправление пользователя некуда записать, кроме истории диалога.

**Что должно было бы оказаться правдой, чтобы выбрать его:** вся база помещается в окно с запасом (≲40 стипендий, ≲100k токенов) и **не растёт**; вход стоит на порядок дешевле, чем сейчас; модель надёжно цитирует и сама держит политику конфликтов (проверено бы на M7 ≥90 % и 0 тихих перезаписей); исправлений пользователей нет. Тогда простота (нет схемы, нет валидатора) перевесила бы.

### B. Плоская база извлечённых фактов без L0 (храним только результат извлечения)

**Почему отказались:** без снимка нельзя проверить цитату кодом (M8) и вычистить отравление аудитом (S6 — именно аудит по L0 нашёл подложенный факт); смена промпта или модели требует заново загружать сайты, которые уже изменились — eval перестаёт быть воспроизводимым; нельзя дешёво перепроверять по хэшу.

**Что должно было бы оказаться правдой:** хранить тексты страниц запрещено (ToS, правовые ограничения) или они слишком велики; извлечение настолько надёжно, что проверка цитат не нужна; eval не нуждается в заморозке (страницы не меняются). Тогда экономия хранения и простота схемы перевесили бы.

### C. Векторная память по чанкам страниц (RAG) без структурированных фактов
Ответ: поиск ближайших чанков → модель отвечает по ним.

**Почему отказались:** главный факт — дедлайн — структурирован (дата, точность, тип, цикл, область); семантический поиск по чанкам охотно возвращает прошлогодний чанк («deadline was 16 February 2026»), а статус цикла и «через N дней» нельзя посчитать кодом без извлечённой структуры; нет места для политики конфликтов и исправлений; провенанс — на уровне чанка, а не факта.

**Что должно было бы оказаться правдой:** вопросы в основном открытые и объяснительные («какие требования к мотивационному письму»), а не про поля с датами и суммами; структурная схема фактов невозможна или слишком дорога в поддержке. Тогда RAG по L0 был бы проще и дешевле. (Векторный поиск по L0 остаётся возможным *дополнением* для открытых вопросов, не заменой L1.)

### D. Карточка L2 как единственный источник истины (изменяемая запись, без L1)
Новая информация правит карточку на месте.

**Почему отказались:** каждое обновление — перезапись: исчезает старое значение и его источник (M7 — тихие перезаписи), исправление пользователя нельзя отменить (S5), нельзя понять, откуда в карточке значение; отравленная запись не отличима от правильной.

**Что должно было бы оказаться правдой:** у каждой стипендии ровно один источник, конфликтов не бывает, пользователи ничего не правят, история изменений никому не нужна.

### E. LLM-управляемая память (модель сама решает добавить, обновить или удалить запись)

**Почему отказались:** решение «перезаписать или сохранить оба» принимает модель — это прямо противоречит требованиям «статус цикла кодом» и «без тихих перезаписей»; поведение недетерминировано и плохо воспроизводится в eval; обновление памяти — дополнительные вызовы модели на каждый факт (стоимость).

**Что должно было бы оказаться правдой:** память в основном о предпочтениях пользователя и ходе диалога, а не о проверяемых фактах о внешних объектах; ошибка в памяти дешёвая (не дедлайн); бюджет позволяет лишние вызовы.

## Последствия

**Плюсы:** провенанс и проверка цитаты кодом (M6, M8); противоречия и исправления видны и обратимы (M7, M9, S4, S5); отравление вычищается аудитом по L0 со следом (S6); контекст ответа ограничен 16k и предсказуем (S7); перепроверка дешёвая — модель только при изменении sha256; eval воспроизводим на снимках.

**Минусы и цена:** схема и валидатор — код, который надо поддерживать; L0 занимает место (~1,8M токенов текста — единицы МБ, приемлемо); политика противоречий жёстко закодирована — новые случаи требуют изменения правил (ADR-002); неверная *интерпретация* с подлинной цитатой (тип даты) аудитом не ловится — закрывается схемой, eval-ловушками и перепроверкой сильной моделью.

**Как проверяем, что решение работает:** сценарии S2–S7 (`python -m harness scenarios`), метрики M6/M7/M8/M9 на видимой части; пересмотр решения — если M7 или M9 не достигают целей при работающем извлечении (M4 ≥ цели), либо если стоимость поддержки схемы превысит выигрыш (например, база останется ≲40 стипендий — тогда вариант A).
