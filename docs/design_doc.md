# Design doc: Research-агент с рабочей тетрадью для поиска стипендий на магистратуру

## 1. Контекст проекта

### 1.1 Бизнес-задача

- **Проблема.** Абитуриент, поступающий в зарубежную магистратуру, 4–9 месяцев ищет и отслеживает стипендии. Проблема двойная:
  - **Покрытие.** Стипендий сотни: государственные, фондовые, вузовские, региональные. Агрегаторы показывают в основном крупные; вузовские стипендии и гранты фондов приходится выкапывать на сайтах программ. Человек находит 15–30 вариантов и пропускает остальные, просто потому что не знал о них.
  - **Актуальность.** Факты по найденным (дедлайн, сумма, требования) разбросаны по официальным сайтам, PDF и агрегаторам, которые отстают на год и копируют друг друга с ошибками. Таблица, которую ведут руками, через 1–2 месяца перестаёт быть достоверной: непонятно, откуда цифра и когда её проверяли.
- **Почему без LLM-системы не справиться.**
  - **Поиск и агрегаторы** выдают страницы, но не отбирают под профиль, не сводят факты и не замечают противоречий.
  - **Правила и регулярки** не извлекут дедлайн и условия из свободного текста на 4–5 языках и из PDF с разной вёрсткой.
  - **Готовые продукты** (Mastersportal, Scholarship Portal) покрывают только свою базу и сами являются источником расхождений.
- **Почему именно это решение имеет смысл.** Клиент платит за два результата одновременно:
  1. **Найти как можно больше стипендий, подходящих под профиль**, включая те, которых нет в топе агрегаторов.
  2. **По каждой найденной держать факты актуальными и прослеживаемыми**: источник, дата, уверенность; противоречия разрешаются явно и остаются видимыми.

  Одно без другого не работает: большой список с неверными дедлайнами хуже короткого верного, а верный короткий список теряет деньги на непройденных вариантах. Поэтому discovery и refresh — равноправные части MVP. П


**Критерии успеха для пользователя**:
- Подходящих стипендий найдено как минимум в 2 раза больше, чем пользователь нашёл сам за то же время.
- 0 пропущенных или неверно известных дедлайнов среди отслеживаемых стипендий за сезон.
- Время на поиск и поддержание списка ≤ 3 ч/мес против ~20+ ч/мес вручную.
- По любой цифре в списке за ≤ 1 клик видно, откуда она и когда проверена.

### 1.2 Пользователи и сценарии использования

- **Кто.**
  - Студенты 3–4 курса и выпускники российских вузов технических направлений, которые поступают в магистратуру в ЕС, UK, США или Канаду.
  - Тип пользователей — внешние клиенты.
- **Через что.** Telegram-бот: целевая аудитория уже там, туда же удобно слать уведомления о новых стипендиях и изменениях. Для разработки и eval — CLI с тем же входом.
- **Нагрузка.**

| Единица | На пользователя в месяц | Пилот (30 чел.) в месяц |
|---|---|---|
| Answer (вопрос по тетради) | ~60 | ~1 800 |
| Refresh (перепроверка одной стипендии; ~60 шт. × раз в 2 недели) | ~120 | ~3 600 |
| Discovery (проход поиска новых под профиль, 2 раза в неделю) | ~8 | ~240 |

  - Сезонность: пик в ноябре–январе, когда закрывается большинство дедлайнов.
  - Пиковый интерактивный RPS в пилоте < 0,05. Refresh и discovery идут фоном по расписанию и размазываются по ночи.
- **Цена ошибки.** Высокая и асимметричная.
  - Неверный дедлайн (особенно более поздний, чем на самом деле) или ложное «подходите по гражданству» ведут к потере стипендии или неделям впустую потраченной подготовки.
  - Пропущенная подходящая стипендия — прямая упущенная выгода.
  - Ложное «не подходите» и нерелевантные кандидаты менее опасны, но тратят время и подрывают доверие.
  - Отсюда строгий контракт: без источника факт не выдаём, при сомнении эскалируем.
- **Что для пользователя «хорошо».** Нашёл варианты, о которых не знал; не пропустил дедлайн; не тратит вечера на поиск и перепроверку; доверяет списку, потому что видит источник и дату.

Общение на русском. Источники на английском, немецком, нидерландском, французском; цитаты из них приводятся на языке оригинала.
### 1.3 Границы, ограничения и допущения

| Внутри (наш код, наши данные) | Снаружи (без гарантий) |
|---|---|
| Тетрадь (L0/L1/L2), правила сведения фактов и разрешения конфликтов, discovery и отбор под профиль, планировщик, промпты, бот, eval-корпус | LLM-провайдер, поисковый API, сайты вузов, фондов и агрегаторов, Telegram, Wayback Machine |

**Не делаем:**
- мотивационные письма и подачу заявок;
- визовые и юридические консультации, гарантии зачисления;
- контент за логином или пейволлом;
- рейтинги «престижности»;
- ответы вне домена стипендий.

**Непроверенные допущения:**
- Под типичный профиль есть десятки–сотни подходящих стипендий, у большинства есть официальная страница с извлекаемыми фактами.
- Wayback Machine покрывает ≥ 70% нужных страниц прошлых лет.
- Профиль без ФИО и контактов можно передавать LLM-провайдеру с согласия пользователя.
- Скрейпинг агрегаторов допустим их ToS (проверить).

*Вне домена* (визы, жильё, «какой вуз лучше») — отказ с указанием, куда обратиться. Неверный ответ здесь опасен для пользователя и подрывает доверие к остальным фактам.

## 2. Контракт сервиса

### 2.1 Контракт

| Поле | Что обещаем | Метрика |
|---|---|---|
| **Вход** | Профиль (гражданство, степень, направление, GPA со шкалой, языковые сертификаты, страны, год); команды «найди / отслеживай / перепроверь / удали»; вопросы на русском или английском. Остальное — отказ | M8 |
| **Discovery** | 2 раза в неделю и по запросу находит стипендии под профиль — с агрегаторов, сайтов вузов и фондов. Каждая с официальным источником, без дублей | M13, M14, M10 |
| **Факты** | По каждой стипендии: дедлайн, сумма (значение + валюта + период), требования, что покрывается. У каждого факта: источник, дата проверки, уверенность, статус (`confirmed` / `conflict` / `stale` / `unverified`) | M1, M2, M3, M9 |
| **Противоречия** | Оба значения сохраняются и показываются; выбранное помечено с правилом выбора (официальный > агрегатор, свежее > старое) | M4, M5, M6 |
| **Свежесть** | Факт старше порога (30 дней; 7 дней, если до дедлайна < 45 дней) помечается `stale` | M7 |
| **Ответы** | Только из тетради, со ссылками. Нет данных → «не знаю, могу проверить» | M8 |
| **Эскалация** | Неразрешимый конфликт по дедлайну или eligibility при дедлайне < 30 дней → «проверьте вручную» + черновик письма в приёмную комиссию | M11 |
| **Не обещаем** | Полноту 100%, безошибочность, юридическую силу, итоговое решение по eligibility | дисклеймер в боте |
| **Нефункциональные** | Answer: TTFT P95 ≤ 3 с, e2e P95 ≤ 15 с. Refresh ≤ 3 мин, discovery ≤ 30 мин (фон). ≤ $25 на пользователя в месяц | 3.2, 3.3 |

**Контракт одной фразой:**

> Агент находит стипендии под профиль (≥ 70% эталонного списка, ≥ 80% найденного действительно подходит) и ведёт по каждой факты с источником и датой проверки. Расхождения показаны явно, устаревшее помечено. На вопросы бот отвечает только из тетради, без данных — говорит об этом. TTFT ≤ 3 с, ответ ≤ 15 с (P95). Вне домена не отвечает.

### 2.2 Сценарии

**Основные**

| Сценарий | Пример | Результат |
|---|---|---|
| Discovery | «Найди стипендии по CS в Германии» / по расписанию | Новые стипендии с ключевыми фактами и пометкой «подходит / неясно» |
| Вопрос по тетради | «Какие дедлайны в ноябре?» | Список с источниками и пометками свежести и конфликтов |
| Refresh | «Перепроверь всё до января» / по расписанию | Что изменилось, новые конфликты |
| Конфликт | «На Mastersportal другая дата, кто прав?» | Обе даты, выбранная и почему |
| Изменение профиля | «Сдал IELTS 7.0» | Пересчёт eligibility + внеочередной discovery |

**Исключительные**

| Ситуация | Что видит пользователь |
|---|---|
| Данных нет в тетради | «В тетради этого нет. Поискать?» |
| Discovery ничего не нашёл | «Новых подходящих нет, следующая проверка [дата]» — без добивания мусором |
| Запрос неоднозначен | Один уточняющий вопрос с вариантами |
| Вне домена | Отказ + куда обратиться |
| Сайт или поиск недоступен | 2 ретрая → альтернативный источник → «данные от [дата], не перепроверены» |
| Невалидный формат / исчерпан лимит шагов | Частичный результат: «перепроверено 3 из 5 полей» |
| Пользователь утверждает ложный факт | Сверка с источником: «в источнике значение другое — ссылка» |

### 2.3 Диалог и память

- **Multi-turn.** В промпт идут последние 6 сообщений.
- **Где живёт память.** В Postgres: тетрадь L0/L1/L2, профиль, журнал discovery (что уже искали), история диалога. В контекст всегда попадает L2, L1 — по запросу, L0 — только при споре. Модель между вызовами ничего не помнит.
- **Профиль между сессиями** хранится с согласием пользователя; есть команда удаления данных.
- **Тон.** Русский, на «вы», кратко: факт → источник → дата. Маркеры статуса: 🆕 новая, ⚠️ конфликт, 🕓 устарело.
- **Прозрачность.** Бот сразу сообщает, что он бот и что перед подачей факты нужно проверять по официальной ссылке.

## 3. Бюджеты

### 3.1 Качество

| ID | Метрика | Как считаем | Цель | Откат |
|---|---|---|---|---|
| M1 | Точность фактов | Совпадение с GT-актуальным (дата — точно; сумма — значение + валюта + период) | ≥ 90% дедлайны, ≥ 85% остальное | < 85 / 80% |
| M2 | Обоснованность | Значение есть на указанной странице/снапшоте | ≥ 95% | < 90% |
| M3 | Атрибуция | У факта есть URL + дата + уверенность | 100% | < 100% |
| M4 | Recall конфликтов | Доля GT-противоречий, где показаны оба значения | ≥ 85% | < 75% |
| M5 | Precision конфликтов | Доля флагов `conflict`, которые реальны | ≥ 80% | < 70% |
| M6 | Выбор при конфликте | Доля GT-конфликтов с верно выбранным значением | ≥ 85% | < 75% |
| M7 | Нарушения свежести | Устаревший факт подан как актуальный | 0 | > 0 |
| M8 | Корректный отказ | Нет данных / вне домена → отказ, а не выдумка | ≥ 90% | < 85% |
| M9 | Валидность формата | Запись проходит JSON-схему (после ≤ 1 повтора) | 100% | < 95% |
| M10 | Чистота базы | Дубли; записи без официального источника | ≤ 3%; 0% | > 5%; > 0% |
| M11 | Точность eligibility | Precision «подходит» на парах «профиль × стипендия» | ≥ 80% | < 70% |
| M12 | Ремедиация отравления | Ошибочный факт всплывает после исправления | 0% | > 0% |
| M13 | Покрытие discovery | Доля эталонного списка для тестового профиля, которую нашёл агент | ≥ 70% | < 55% |
| M14 | Релевантность discovery | Доля найденного, что реально подходит под профиль | ≥ 80% | < 70% |

### 3.2 Задержка

API-модель, TPOT ~15 мс.

**Answer** (интерактив):

| Этап | мс |
|---|---|
| Сеть + Telegram + шлюз | ~100 |
| Чтение тетради (SQL) | 50–150 |
| Роутер (дешёвая модель) | 400–700 |
| Prefill ~8k токенов | 600–1 200 |
| Decode 350 токенов × 15 мс | ~5 300 |
| **TTFT P50 / P95** | **~1,5 / ~2,8 с** |
| **e2e P50 / P95** | **~7 / ~12 с** |

**Фоновые задачи:**

| Задача | Из чего складывается | e2e P50 / P95 |
|---|---|---|
| Refresh одной стипендии | 3 поиска, 4 страницы, 4 извлечения (параллельно), сведение сильной моделью | ~35 с / ~90 с |
| Discovery-проход | 20 поисков, до 30 страниц, ~25 вызовов отбора (батчами), ~5 финальных проверок | ~2 / ~5 мин |

**Цели:**
- Answer: TTFT ≤ 3 с, e2e ≤ 15 с (P95), со стримингом.
- Refresh ≤ 3 мин, discovery ≤ 30 мин, без стриминга — по готовности приходит уведомление.

### 3.3 Стоимость

```
cost_per_unit  = Σ (tokens_in × price_in + tokens_out × price_out) + поиски × price_search
cost_per_month = Σ cost_per_unit × units_per_month
```

Допущения по ценам (заменить на актуальные на дату сдачи):
- сильная модель — $3 / $15 за 1M токенов (вход / выход);
- дешёвая — $1 / $5;
- поиск — $0,008 за запрос.

Конфигурация **«гибрид»**: поиск, отбор и извлечение — дешёвая модель; сведение фактов, финальная проверка кандидатов и ответ — сильная.

| | Answer | Refresh | Discovery |
|---|---|---|---|
| Токены вход (дешёвая + сильная) | 1k + 8k | 44k + 6k | 220k + 30k |
| Токены выход | ~0,4k | ~4k | ~18k |
| Поисков | 0 | 3 | 20 |
| **$ за единицу** | **0,03** | **0,11** | **0,60** |
| Единиц на пользователя в месяц | 60 | 120 | 8 |
| **$ на пользователя в месяц** | 1,9 | 13,2 | 4,8 |

**Итого:** ≈ **$20 на пользователя в месяц**; гипотетическая группа из 30 человек — ≈ $600/мес.

| Конфигурация | $/мес на пользователя |
|---|---|
| Всё на сильной | ~33 (выше бюджета) |
| **Гибрид** | **~20** |
| Всё на дешёвой | ~14 (риск по M6, M14) |

**Лимиты (стоп-критерии):**

| Задача | Лимиты | При исчерпании |
|---|---|---|
| Answer | 4 шага, 15k токенов | Ответ по имеющемуся |
| Refresh | 12 шагов, 6 страниц, 60k токенов | Недоделанное — `unverified` |
| Discovery | 40 шагов, 30 страниц, 20 поисков, 300k токенов | Найденное + «не завершено», следующий проход продолжает |

**Скрытая стоимость:**
- разметка корпуса и эталонных списков — ~40–50 человеко-часов;
- прогоны eval за курс — ~$250;
- VPS — ~$5–10/мес.

### 3.4 Компромисс

Главное — **покрытие и точность фактов**: пропущенная или неверно описанная стипендия стоит пользователю тысячи евро, а лишние минуты фоновой работы ничего не стоят. Поэтому:
- discovery идёт широко, но на дешёвой модели;
- сильная модель — только там, где ошибка дорогая: сведение фактов, конфликты, решение «заводить ли стипендию»;
- задержкой фоновых задач жертвуем полностью;
- стоимость держим в пределах $25 на пользователя в месяц через частоту refresh (~65% бюджета) и остановку discovery, когда новых кандидатов нет. Модель на сведении не удешевляем.

## 4. Архитектура (набросок)

```
[Telegram-бот / CLI для eval]
          │
       [LiteLLM: роутинг моделей, ретраи, учёт стоимости]
          │
   [оркестратор] ── Router ──┬── Answerer (только чтение тетради)
                             ├── Discovery-агент
                             └── Refresh-агент
                                   │ web_search, fetch_page, extract_facts, notebook_*
                                   ▼
 ┌──────────── ТЕТРАДЬ (Postgres) ────────────┐
 │ L2 резюме по стипендиям + дайджест         │ ← всегда в контексте
 │ L1 факты: значение, источники, статус,     │ ← по запросу
 │    история изменений                       │
 │ L0 сырые выписки с URL и датой (неизм.)    │ ← при споре
 │ + журнал discovery                         │
 └────────────────────────────────────────────┘
   ▲ планировщик: discovery 2×/нед, refresh по свежести и близости дедлайна
 ───────────── наблюдаемость: Langfuse ─────────────
```

**Ключевые правила** (уходят в ADR):
- Факт поднимается L0 → L1 → L2 только через reconciler с явным правилом приоритета источников.
- Исправление делается в L1 с записью в историю, затем L2 пересобирается. Так ошибка не тиражируется по ответам.
- Новая стипендия заводится только с официальным источником и после дедупликации.

**Запланированные ADR:**
- ADR-001 — уровни тетради;
- ADR-002 — политика при противоречии;
- ADR-003 — право завести стипендию;
- ADR-004 — фреймворк оркестрации.
