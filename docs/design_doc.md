## 1. Контекст

### 1.1 Бизнес-задача
**Проблема.** Абитуриент (магистратура STEM/IT: ЕС, UK, США, Канада) 4–6 мес. собирает стипендии. Вручную находит 20–40 из сотен релевантных; агрегаторы устаревают и расходятся с официальными сайтами; таблица теряет источники и даты. Ошибка в дедлайне = потерянный год.

**Почему LLM-система.** Агрегаторы не фильтруют по профилю и не показывают источник/дату; скрейперы ломаются на разнородных страницах, условия написаны свободным текстом; разовый чат или deep research не хранит состояние и не отслеживает изменения.

**Альтернативы без системы** (на 3 мес, база ~150–200 стипендий):

| Альтернатива | Стоимость | Минус |
|---|---|---|
| Вручную + Excel | ≈75 ч: старт 150 × 20 мин ≈ 50 ч + ~12 ч/мес перепроверок | на практике до такого объёма никто не доходит, база устаревает |
| Только агрегаторы | 0, ~10–15 ч | старые даты, нет фильтра и учёта; часть дат противоречит официальным (см. `docs/spike_kt2.md`) |
| Консультант | [собрать цены, см. 11] | дорого, узкий охват |
| **Система** | ≈ $8 старт + ≈ $7/мес (3.3) | — |

**Успех для пользователя:** найдено ≥2× больше релевантных стипендий, чем вручную (≥150 записей с официальным источником, покрытие ≥70 % эталонного списка); ≤2 ч/мес времени пользователя; 0 пропущенных дедлайнов из-за неверной даты; у каждого факта есть источник и дата.

### 1.2 Пользователи и нагрузка
- **Кто:** русскоязычные студенты 3–4 курса бакалавриата и выпускники, поступающие в зарубежную магистратуру по STEM/IT (ЕС, UK, США, Канада). Готовят заявки 4–6 мес., рассматривают 10–30 программ, часть стипендий требует отдельной подачи.
- **Масштаб MVP:** до 4 профилей (2 разработчика с реальными профилями + до 2 проверяющих); одна общая база (факты о стипендиях не персональны), профиль работает как фильтр.
- **Канал:** чат (Telegram или веб) + фоновые запуски по расписанию; экспорт в CSV.
- **Нагрузка в месяц** (уменьшена в v0.2: учебный проект, бюджет на API минимальный):
  - старт: ~400 лидов (названий из поиска) → ~250 кандидатов с официальной страницей → ~150 записей;
  - далее: ~100 лидов → ~60 кандидатов; ~900 загрузок страниц для перепроверки, из них ~135 изменились и идут в модель;
  - ~150 вопросов от пользователей + eval: 2 полных прогона (100 страниц + 120 запросов) и 4 smoke-прогона по 20 запросов;
  - пик в ноябре–январе.
- **Цена ошибки:**
  - дедлайн показан позже реального или прошлогодний выдан за текущий — **критично**;
  - неверная eligibility (10–20 ч на заявку впустую) — **высокая**;
  - стипендия не найдена — **высокая**;
  - неверная сумма — **средняя**.

### 1.3 Границы и допущения

| Внутри | Снаружи (не гарантируем) |
|---|---|
| тетрадь, правила подъёма фактов и разрешения конфликтов, профили, оркестратор, планировщик, eval | сайты фондов и агрегаторов, поисковый API, LLM-провайдер, решения комиссий |

**Не делаем:** подачу заявок, письма и CV, оценку шансов, визовые и юридические вопросы, PhD и бакалавриат.

**Допущения** (✔ — проверено в спайке `docs/spike_kt2.md`):
- у ≥80 % стипендий есть официальная страница с дедлайном — ✔ частично: дедлайн часто на подстранице или на странице страны;
- за месяц меняется ~15 % страниц — не проверено, измерим по логам перепроверки (КТ3);
- снапшоты 2024–2026 доступны в Wayback Machine — ✔ (запросы последовательно);
- доступ к API с оплатой есть — ✔ Tavily (бесплатный тариф), OpenAI для тестов; провайдер выбирается в ADR-004;
- robots.txt и ToS позволяют читать страницы — ✔ для официальных сайтов из выборки; 2 из 3 агрегаторов блокируют ботов;
- пользователь один раз заполняет профиль;
- заметная часть стипендий может быть закрыта для граждан РФ — проверяется при разметке (поле `open_to_ru`).

## 2. Контракт

M1–M11 — идентификаторы метрик из 3.1; на них ссылаются контракт, SLO и eval-сет. Изменения v0.2 по итогам спайка (`docs/spike_kt2.md`) отмечены в «Истории изменений».

### 2.1 Контракт

| Поле | Обещание | Метрика |
|---|---|---|
| Вход | Вопросы и команды на RU/EN о стипендиях на магистратуру в рамках профиля («найди ещё», «дедлайн X», «покажи расхождения», «исправь»). Остальное — отказ. | M8 |
| Покрытие | Discovery по профилю находит ≥70 % стипендий из эталонного списка к защите (≥50 % к КТ3). | M1 |
| Выход | Каждый факт = значение + URL + дата проверки + статус (`подтверждён` / `вероятен` / `конфликт` / `устарел`) + дословная цитата из источника. | M6, M8 |
| Дедлайн | Дедлайн подачи = дата + точность (день / месяц) + цикл (intake 2027) + область (общий / страна / вуз / программа / группа заявителей). Дату оффера, результатов или открытия приёма не выдаём за дедлайн подачи. Если дедлайн задаётся по стране или вузу — показываем значение для профиля, а если его нет в тетради — явно «зависит от …» со ссылкой. | M4 |
| Сумма | Основная выплата (сумма, валюта, период) или признак полного покрытия; бюджет программы целиком не выдаётся за выплату. | M5 |
| Противоречия | Не затираются, оба значения хранятся. Приоритет: официальный > университет > агрегатор; новый цикл > старый. Официальный источник старее и расходится → `конфликт`, показываем оба. | M7 |
| Новая запись | Нужны: официальная страница (фонд, вуз, госорган); известны фонд или вуз; пройдены фильтры (магистратура, направление, гражданство не исключено, цикл ≥ текущего). Агрегаторы и блоги — только источник названий («лиды») и пополнение «кандидатов». | M3, M10 |
| Статус цикла | Вычисляется кодом по извлечённым датам, а не моделью: `подтверждён` — есть дедлайн подачи цикла 2027; `устарел` — только прошлый цикл; `не подтверждено` — дат нет. | M4 |
| Неуверенность | «Не подтверждено для цикла 2027» + ссылка; дедлайн не выдумывается и не переносится из прошлого цикла. | M4, M8 |
| Исправление пользователя | Пишется как факт с источником «пользователь, дата» и участвует в политике конфликтов; все следующие ответы его учитывают. | M9 |
| Не обещаем | полноту сверх целевого покрытия, итоговое решение по eligibility, шансы, юридическую силу | дисклеймер |
| Нефункциональные | чат: TTFT ≤2 с, e2e ≤15 с (P95); перепроверка ≤90 с; свежесть ≤14 дней, для дедлайнов ≤30 дней — ≤72 ч | 3.2, M11 |

### 2.2 Сценарии

| Сценарий | Пример | Результат |
|---|---|---|
| Discovery | «Найди стипендии по CS в Германии» | +N записей, M в кандидатах (с причиной) |
| Факт | «Дедлайн Eiffel на 2027?» | дата + цикл + область + ссылка + статус |
| Дедлайн по стране | «Дедлайн Chevening?» | «октябрь 2026, точная дата — на странице страны» + ссылка; дата оффера не выдаётся за дедлайн |
| Срочное | «Что закрывается за 30 дней?» | отсортированный список |
| Конфликт | «Почему дата не как на агрегаторе?» | оба значения, источники, правило выбора |
| Исправление | «Дедлайн 1 ноября, я звонил» | сохранено, конфликт с официальным виден |
| Перепроверка | «Проверь Holland сейчас» | diff с тетрадью |

| Исключение | Поведение |
|---|---|
| факта нет на страницах | `не указано` (неизвестно, а не «не существует»), ссылка на официальную страницу |
| только прошлый цикл | `устарел`, цикл указан явно |
| дедлайн без года на странице | год не достраивается; дата хранится с точностью «день, год неизвестен» и статусом `вероятен`, пока цикл не подтверждён контекстом страницы |
| сайт блокирует бота (403) или отдаёт JS-оболочку | Tavily Extract как запасной путь; если и он не смог — запись остаётся в «кандидатах» с причиной |
| несуществующая стипендия | «стипендия не найдена», 0 записей |
| вне домена | отказ по контракту |
| сайт / API недоступен | 2 ретрая, показ последнего значения с датой |
| невалидный JSON | 1 повтор, затем в кандидаты с флагом |
| зацикливание агента | лимит шагов и бюджета, частичный отчёт |
| эскалация | оператора нет; `конфликт` и `не подтверждено` у ближайших дедлайнов идут в блок «требует внимания» |

### 2.3 Диалог и память
- **Режим:** multi-turn.
- **История:** последние ~10 реплик, ≤3k токенов, старое сворачивается в резюме.
- **Где живёт память:** в хранилище (тетрадь L0–L3 + профили + журнал сессий). Что подгружать, решает оркестратор; модель сама ничего не помнит.
- **Профиль:** хранится с согласия, его можно посмотреть и удалить.
- **Тон:** русский, коротко, сначала ответ, потом источники, без обещаний шансов.
- **Прозрачность:** пользователь знает, что это бот; у каждого факта видна дата проверки.

### 3.1 Качество
Эталон (GT), состав eval-сета и процедура разметки — в разделе 7. Здесь — метрики и пороги.

| ID | Метрика | Пункт контракта | Как считаем | Цель | Откат |
|---|---|---|---|---|---|
| M1 | Покрытие | Покрытие | доля эталонного списка (раздел 7, часть A1), найденная discovery по профилю; прогон вживую, дата фиксируется | ≥50 % к КТ3, ≥70 % к защите | <40 % |
| M2 | — | — | **исключена в v0.2**: объём не является обещанием контракта и раздувается гранулярностью записей; ориентир объёма остаётся в 1.2 | — | — |
| M3 | Релевантность | Новая запись | доля записей, прошедших фильтры профиля, по ручной проверке случайной выборки 50 записей | ≥85 % | <75 % |
| M4 | Дедлайн | Дедлайн, Статус цикла, Неуверенность | **по каждой стипендии A2 (100 решений)**: верны статус цикла (`подтверждён` / `устарел` / `не подтверждено`) и множество дедлайнов подачи (дата, точность, область). **Опасная ошибка** — дата позже реальной, дата прошлого цикла выдана за текущую или выдуман дедлайн там, где в эталоне его нет | ≥90 %; опасных ≤1 на 100 стипендий | опасных >3 на 100 |
| M5 | Сумма | Сумма | совпадение основной выплаты (сумма + валюта + период) или признака полного покрытия с A2 | ≥80 % | <70 % |
| M6 | Провенанс | Выход | у факта есть URL, дата проверки, статус и цитата; проверка схемой | 100 % | <98 % |
| M7 | Конфликты | Противоречия | на парах A3: верно выбрано / оба значения показаны / тихие перезаписи | ≥90 % / ≥95 % / 0 | <80 % / <90 % / >0 |
| M8 | Выдумки и отказы | Выход, Вход, Неуверенность | (а) доля фактов, цитата которых не найдена в снимке страницы (L0) — правило в коде, без judge; (б) на несуществующих стипендиях и запросах вне домена — «стипендия не найдена» / отказ и 0 новых записей; (в) **связь «значение — цитата — тип — цикл — область»**: на случайной выборке 30 фактов прогона проверяющий LLM-агент другой модели, чем экстрактор, по снимку отвечает, подтверждает ли цитата именно это значение (`docs/m8c_checker_prompt.md`, `eval/scripts/m8c.py`) | (а) ≤2 %; (б) 100 %; (в) ≥95 % | (а) >5 %; (б) <95 %; (в) <90 % |
| M9 | Исправления | Исправление пользователя | (а) многоходовые истории B категории «исправление и память» (7 видимых): эталон — критерии «обязательно / недопустимо» **на историю**, история засчитывается, если ответы после исправления их выполняют; (б) сценарий S5: 5 повторных чтений карточки после исправления, переход через границу сессии и отмена | 100 % | <100 % |
| M10 | Дубли | Новая запись | на парах A4 (алиасы и похожие, но разные стипендии): доля склеенных разных + не склеенных одинаковых | ≤3 % | >7 % |
| M11 | Свежесть | Нефункциональные | дедлайны ≤30 дней перепроверены за 72 ч — **SLO по телеметрии** (КТ4), на фиксированном наборе не считается | ≥95 % | <85 % |

**Уточнения после ревью КТ2.**
- **Нормализация общая.** Дата и её точность, валюта, период выплаты и признак полного покрытия приводятся к одному виду одним кодом (`harness/rules.py`). Его вызывают системы (B1, LLM-извлечение, тетрадь) и оценщик, и для предсказания, и для эталона. Расхождение в написании («€» / «EUR», «monthly» / «month») не влияет на M4 и M5.
- **«Неизвестно» ≠ «не существует».** Исходы разделены. Дедлайн: `published` (цикл 2027/28) / `only_past_cycle` / `cycle_unknown` (дата есть, цикл из страницы не следует) / `not_stated` (на страницах нет — это незнание, а не отсутствие дедлайна). Сумма: `stated` / `full_coverage_only` / `not_stated`; `full_coverage: null` («страница не говорит») ≠ `false` («прямо сказано: частичное»). «Стипендия не найдена» (поиск пуст) — отдельный исход агента, в карточке он не появляется. M4 и M5 отчитываются с разбивкой по исходам. Опасная ошибка «выдуман дедлайн» разделена на `invented` (на странице дедлайна нет) и `year_guessed` (дата без года, а система достроила год).
- **M9 сужена до того, что проверяет набор.** Видимые истории B — 2–4 реплики с одним ожиданием на историю, поэтому «5 контрольных вопросов» в них нет. 5 повторных чтений после исправления проверяются сценарием S5. Граница сессии задана явно (6.4) и тоже проверяется в S5.
- **M8(в)** — новая проверка связи цитаты со значением (см. таблицу). Проверяет агент, а не человек: подвыборка небольшая, а проверяющий работает на другой модели, чем экстрактор.

**Почему M4 считается по стипендиям и почему опасные — «на 100».** Разметка показала: у 50 из 100 стипендий на официальных страницах вообще нет дедлайна подачи, у 29 есть дедлайн цикла 2027/28 (всего 69 дедлайнов). Считать по дедлайнам — значит не проверять самый частый случай «дат нет», где опасная ошибка — выдумать дату. Поэтому единица M4 — стипендия: 100 решений. На такой выборке 0 и 1 % статистически не различимы: при 0 ошибках верхняя граница 95 % доверительного интервала ≈3 % (правило трёх). Поэтому цель — не больше одной опасной ошибки, а откат — только при явной проблеме (>3), а не при первой же ошибке.

**Бюджет контекста.** Тетрадь в ~10 раз больше окна модели (200k), поэтому нужна иерархия.

Объём тетради к защите (~200 записей, ~3 страницы на запись):

| Уровень | Что лежит | Объём | Попадает в промпт |
|---|---|---|---|
| L0 | снимки страниц (текст после trafilatura + хэш + дата) | ≈1,8M токенов | только при переизвлечении |
| L1 | атомарные факты с цитатами и источниками | ≈0,5M | по запросу (источник, конфликт) |
| L2 | карточки стипендий | ≈160k | до 8 карточек через retrieval |
| L3 | резюме: профиль, топ, ближайшие дедлайны | ≤3k | всегда |

Лимит на один ответ — **≤16k входных токенов**: системный промпт + инструменты 2,5k, профиль 0,5k, L3 ≤3k, карточки ≤6,5k, история ≤3k.

### 3.2 Задержка

| Этап (ответ по тетради) | мс |
|---|---|
| сеть + шлюз | 50–100 |
| retrieval (SQLite FTS / вектора) | 50–150 |
| prefill ~12k (TTFT, API) | 500–1500 |
| decode 600 ток × 10–15 мс | 6000–9000 |
| шагов | 1–2 |
| **e2e P50 / P95** | **~7 с / ~13 с** |

Цели:
- **чат:** TTFT P95 ≤2 с, e2e P95 ≤15 с, стриминг включён;
- **перепроверка «сейчас»:** ≈20–30 с, P95 ≤90 с;
- **фоновый discovery:** ~25 с на кандидата (основная страница + 1–3 подстраницы; извлечение одной страницы в спайке — 1,3–5 с); стартовые 250 кандидатов при параллелизме 10 ≈ 10 мин, цель ≤1 ч;
- **Batch API** (до 24 ч) допустим для фона и eval, кроме дедлайнов ≤72 ч.

### 3.3 Стоимость
Провайдер ещё не выбран (сравнение — ADR-004, КТ3). Ниже расчёт по ценам Claude как референс; для тестов в спайке использовался `gpt-5.4-mini`, после выбора провайдера таблица пересчитывается по тем же объёмам.

Цены на 04.10.2026:
- Haiku 4.5 — $1 / $5 за 1M токенов; Sonnet — $3 / $15;
- чтение из кэша — 10 % цены входа; Batch API −50 %;
- Tavily: 1000 бесплатных кредитов/мес. Расход ≈340 в первый месяц (≈60 широких поисков + ≈250 поисков официальных страниц + extract) и ≈150 потом — укладывается, поэтому ниже считается только LLM.

**Что снижает стоимость:**
- discovery в два шага: из широкой выдачи берутся только названия, модель читает только официальные страницы;
- отсев лидов по сниппету до загрузки страниц;
- перепроверка: fetch + сравнение хэша текста бесплатно, модель вызывается только при изменении (~15 % страниц);
- статус цикла, даты «через N дней», фильтры — в коде, без модели;
- M8(а) считается правилом (цитата есть в L0), без judge; M8(в) — только на выборке 30 фактов за прогон;
- eval извлечения — на сохранённых снимках страниц, без повторного поиска;
- кэш системного промпта и L3 в ответах; batch для фона и eval.

Токены на страницу замерены в спайке: ≈2,6k входа / 0,6k выхода.

- **Бюджет:** ≤ $10 старт, ≤ $8/мес, ≤ $25 на проект + резерв $10 на отладку (повторные прогоны, эксперименты с промптами) → выбираем B. Переход на C — если ответы дешёвой модели не держат M4/M7 (ADR-004).

- **Скрытые затраты:** эталон размечает LLM-агент (раздел 7.4) — время команды ≈3–4 ч на проверку меток и спорных случаев; ручная проверка релевантности (M3) ≈1 ч на прогон.
- **Self-host:** не рассматриваем — данные публичные, нагрузка мала.

**Пересчёт по факту (КТ3).** Живой прогон извлечения (8.3, три повтора на 70 стипендиях видимой части): 109 страниц за прогон, **≈2,4k токенов входа / 0,41k выхода на страницу** (в спайке было 2,6k / 0,6k; выход включает reasoning-токены). На `gpt-5.4-mini` ($0,75 / $4,50 за 1M) это $0,0036 на страницу, **$0,0056 на стипендию**, $0,39 за полный прогон видимой части. Пересчёт таблиц выше по факту:

Извлечение дешевле плана в 1,5–3 раза. По этой статье конфигурация B (3.3) укладывается в $8/мес с запасом, и запас можно потратить на сравнение 2–3 моделей (шаг 6, 8.2). Ответы (U4), конфликты (U3) и L3 (U5) пока не запускались: их стоимость остаётся оценкой и пересчитывается по телеметрии на КТ4. Задержка извлечения — P50 3,3 с, P95 7,4 с на стипендию (план 3.2: 1,3–5 с на страницу) — укладывается в «фоновый discovery ~25 с на кандидата».

### 3.4 Компромисс
Главное — точность дедлайнов (M4) и покрытие (M1). Стоимость — жёсткое ограничение ($8/мес, $25 на проект): это учебный проект, поэтому масштаб базы уменьшен до ~150–200 записей — для eval и демо этого достаточно, методика оценки от масштаба не зависит. Задержка вторична: тяжёлая работа идёт в фоне. Массовые операции — на дешёвой модели через batch; сильная модель — там, где ошибка тиражируется (конфликты, L3). При нехватке бюджета режем discovery и частоту полных eval, но не перепроверку ближайших дедлайнов. Принимаем более низкую M5 на «хвосте» малых университетских стипендий.

## 4. Архитектура

```
[чат] → [шлюз: бюджет, учёт токенов] → [оркестратор] ← [планировщик: discovery / перепроверка / резюме]
                                            ↓ ↑
                         [LLM API: дешёвая / сильная модель, ADR-004]
                                            ↕
  [тетрадь, общая база]                               [инструменты]
   L0 сырые выписки (неизменяемые, с хэшем)            web search, fetch/extract,
   L1 факты: значение+источник+дата+статус             CRUD тетради, текущая дата
   L2 карточки: разрешённые значения + конфликты
   L3 резюме на профиль: топ, ближайшие дедлайны
   + профили, журнал сессий, кандидаты
  ─────────────── наблюдаемость: трейсы, стоимость, eval (Langfuse) ───────────────
```

| Блок | Готовое | Пишем сами |
|---|---|---|
| Клиент | Telegram Bot API / Streamlit | карточка стипендии |
| Шлюз | LiteLLM / OpenRouter | лимит бюджета системы |
| Оркестратор | PydanticAI / LangGraph | подъём фактов, политика конфликтов, правило заведения |
| Хранилище | SQLite (+ FTS / вектора) | схема L0–L3 |
| Инструменты | Tavily / Brave, trafilatura | дедупликация, сравнение хэшей |
| Наблюдаемость | Langfuse | eval-харнесс на GT |

**Путь вопроса:** L3 + профиль → retrieval до 8 карточек L2 → L1 только для источника, конфликта или исправления → валидация (у каждого факта источник, дата, статус) → стриминг. L0 читается только при переизвлечении.

**Путь discovery** (два шага — по итогам спайка: на широких запросах официальные сайты дают 30 % выдачи и ни разу не в топ-3):
1. широкий поиск (Tavily, `exclude_domains` для соцсетей) → из выдачи берутся только названия стипендий (лиды) → отсев по сниппету;
2. для каждого лида — поиск официальной страницы (запрос по названию, `include_domains` по домену фонда, если он известен) → загрузка основной страницы и подстраниц `timeline|dates|deadline|apply|eligibility` на 1 уровень → L0;
3. L0 → извлечение в L1 (JSON-схема, цитата у каждого значения) → валидатор → правило заведения → дедупликация → L2 → L3 помечается устаревшим и пересобирается.

**Получение текста страницы:** свой fetch (`httpx`, честный User-Agent, robots.txt) + `trafilatura`; Tavily Extract — запасной путь для 403 и JS-оболочек. Подмену User-Agent не используем. Выбор фиксируется в ADR-006.

**Модель данных дедлайна:** `date` (YYYY-MM-DD или YYYY-MM), `granularity` (day / month), `type` (application / offer_or_documents / results / opening / other), `scope` (global / country / university / program / applicant_group) + `scope_detail`, `cycle`, `quote`, `source_url`. У одной стипендии может быть много дедлайнов (Chevening и DAAD — по странам, NL Scholarship и Gates — по вузу или курсу).

**Валидатор после извлечения (код, не модель):** формат даты; цитата буквально есть в L0; статус цикла вычисляется по датам (раздел 2.1); дата открытия приёма не может быть единственным дедлайном подачи. Ошибки спайка, которые он ловит: дата «20 October» без года, статус `подтверждён` без дат (Rhodes, DAAD).

**Путь перепроверки:** fetch → сравнение хэша основного текста с L0 (хэш сырого HTML нестабилен) → если изменилось, новое извлечение в L1 → пересчёт L2.

**Подъём L1→L2:** карточка всегда пересчитывается из L1, поэтому исправление доходит до всех ответов (M9).

**Baseline и план усложнений** — раздел 8.

**Где это в коде (КТ3).** Ядро реализовано в `harness/`. Канал (чат), шлюз, планировщик и живые Tavily/fetch пока не подключены: инструменты работают офлайн на снимках L0 с теми же сигнатурами.

| Блок схемы | Модуль |
|---|---|
| оркестратор: discovery → загрузка → извлечение → валидатор → L1 → L2 | `harness/agent.py` |
| тетрадь L0–L3, журнал, сессии, кэш извлечения | `harness/notebook.py` (SQLite) |
| инструменты и их контракты | `harness/tools.py` |
| LLM-извлечение по JSON-схеме | `harness/systems/llm_extract.py` |
| статус цикла и даты — код | `harness/rules.py` |
| сборка контекста под бюджет | `harness/context.py` |
| baseline B1 | `harness/systems/b1.py` |
| харнесс: раннер, метрики, сценарии | `harness/runner.py`, `metrics.py`, `scenarios.py` |

**ADR** (`adr/`):
- [001](../adr/001-notebook-levels.md) — уровни тетради и подъём факта (**главное решение темы, КТ3**);
- 002 — политика противоречий (правила зафиксированы в 6.5, ADR — КТ4);

## 5. Eval-харнесс

Харнесс — пакет `harness/`, не ноутбук. Всё запускается командами, результат каждого прогона — папка в `runs/` с метаданными.

### 5.1 Один вход

```
python -m harness run --system b1  --suite extract     # baseline B1 на видимой части A2
python -m harness run --system llm --suite extract     # шаг 1: LLM-извлечение (нужен ключ в .env)
python -m harness scenarios                          # многошаговые сценарии S1–S7
python -m harness compare runs/<id1> runs/<id2>        # таблица «до → после»: метрики, стоимость, время
python -m harness contracts                            # таблица контрактов инструментов (5.3)
python -m unittest discover tests                      # тесты трубопровода без сети
```

Любая система реализует один интерфейс `System.run(task, ctx) → (статус, output)` и запускается одним раннером (`harness/runner.py`) на одних и тех же задачах, с одними инструментами, бюджетом и метриками. Baseline и система различаются только классом системы. Метрики считает код по эталону (`harness/metrics.py`), без judge.

**Защита отложенной части.** Раннер берёт задачи только из видимой части (`split.csv`). Инструменты отказываются читать снимки стипендий отложенной части (`not_found`). Метка не из видимой части останавливает прогон.

### 5.2 Воспроизводимость

Прогон сохраняется в `runs/<дата-время>_<система>_<набор>/`:

| Файл | Что |
|---|---|
| `meta.json` | система и её конфигурация: модель с версией (пиннинг по дате), `temperature`, `seed`, `reasoning_effort`, тексты промптов, JSON-схема и их хэш, цены за 1M токенов, правила B1; версия eval-набора (`v1`) и sha256 файлов эталона (`labels_a.jsonl`, `split.csv`, `manifest.csv`, `conflicts.jsonl`, `reference_list.csv`, `duplicates.jsonl`); sha256 видимых снимков и файлов харнесса; упорядоченные ID задач, бюджеты, локальные переопределения и контракты инструментов; git-коммит и признак незакоммиченных изменений; дата заморозки eval (2026-10-25, от неё считается «сегодня»); итоги: стоимость, токены, время всего прогона, P50/P95 на задачу |
| `metrics.json` | агрегированные метрики с 95 % доверительными интервалами |
| `results.jsonl` | по каждой задаче: статус, выход, расход, причина остановки, трейс шагов и вызовов инструментов |
| `per_task.jsonl` | разбор метрик по задаче (для поиска ошибок) |
| `runs/index.csv` | строка на прогон: id, система, модель, коммит, стоимость, время, метрики |

Офлайн-режим детерминирован: страницы — снимки L0 из `eval/gt/pages`, `today()` — дата заморозки набора. Источник недетерминизма один — модель. Для неё фиксируются `seed`, версия модели и промпт; извлечение повторяется 3 раза на 20 страницах для оценки разброса (7.6). Модель без цены в конфигурации не запускается: стоимость прогона обязана считаться.

### 5.3 Контракты инструментов

Ошибка инструмента — всегда `ToolError(tool, code)` с кодом из контракта. Код, которого нет в контракте, — ошибка программы (assert). Лимиты — на одну стипендию. Сценарии, обрабатывающие до 12 стипендий, расширяют их явно, а ограничивает их общий бюджет шагов.

| Инструмент | Сигнатура | Возвращает | Ошибки | Таймаут | Лимит/задачу | Ретраи |
|---|---|---|---|---|---|---|
| list_pages | `list_pages(scholarship_id: str) -> list[str]` | пути снимков L0 стипендии, основная страница первой | not_found, timeout, call_limit | 1 с | 3 | нет: ошибка детерминированная |
| fetch | `fetch(page: str) -> Page(text, url, sha256, fetched_at, page)` | текст страницы после trafilatura + метаданные | not_found, snapshot_error, http_403, http_5xx, timeout, stub_page, call_limit | 20 с | 8 | http_5xx/timeout — до 2 ретраев; http_403/stub_page — без ретрая, сразу запасной путь |
| fetch_alt | `fetch_alt(page: str) -> Page` | запасной путь (Tavily Extract) | not_found, snapshot_error, http_403, timeout, call_limit | 30 с | 4 | нет; при ошибке — последний снимок L0 с его датой или запись в «кандидаты» |
| search | `search(query: str) -> list[Hit(scholarship_id, name, url, score)]` | кандидаты официальной страницы | timeout, rate_limit, catalog_error, call_limit | 15 с | 15 | timeout/rate_limit — 1 ретрай; пустая выдача — не ошибка, а «не найдено» |
| extract_llm | `extract_llm(page_text, url) -> dict` (JSON по схеме) | факты страницы, у каждого значения цитата | invalid_json, timeout, rate_limit, provider_error, call_limit | 60 с | 6 | invalid_json — 1 повтор, затем страница в «кандидаты» с флагом; rate_limit/timeout — 2 ретрая с backoff |
| today | `today() -> str` | текущая дата (в eval — дата заморозки) | timeout, call_limit | 1 с | 50 | не нужен |

`stub_page` — детектор заглушек: текст короче 200 символов или CAPTCHA/«enable JavaScript» в коротком тексте (находка разметки: esteri.it отдавал CAPTCHA с кодом 200). Сбои для сценариев задаются инъекцией: `{"fetch": {"eiffel/1.txt": ["http_5xx", "http_5xx", null]}}` — по попыткам для конкретного аргумента.

### 5.4 Бюджет шагов и критерий остановки

Бюджет на задачу (`harness/core.py`, `Budget`): ≤8 шагов (шаг — вызов модели), ≤20 вызовов инструментов, ≤$0,05, ≤120 с. Счётчик проверяется перед каждым шагом. На лимите следующий шаг не выполняется. Время и стоимость проверяются также после вызова модели. Фактическая стоимость последнего ответа известна после получения usage.

Задача всегда заканчивается одним из статусов, «крутится дальше» невозможно:

| Статус | Когда | Что возвращается |
|---|---|---|
| `ok` | система закончила сама | полный результат |
| `partial` | часть страниц недоступна или не извлеклась | результат + список «кандидатов» с причиной по каждой странице |
| `budget_exhausted` | исчерпан любой лимит | **частичный результат**: что сделано, что осталось (`done` / `remaining`), причина (`steps: 10/10`) |
| `refused` | вне домена по контракту | отказ |
| `error` | необработанная ошибка системы | M4 и M5 отмечают задачу как ошибку. M6 и M8 считают выданные факты. Прогон продолжается |

При `partial` и `budget_exhausted` M4/M5 оценивают найденные значения. Пустой блок в неполном результате не подтверждает отсутствие даты или суммы. Для локальных инструментов таймаут проверяется после операции. Вызов LLM получает таймаут с учётом оставшегося времени задачи.

На исчерпании нет ни эскалации к человеку (оператора нет, 2.2), ни молчаливого обрыва. Пользователь получает частичный отчёт, а незаконченная стипендия не попадает в тетрадь: запись в L1 по стипендии атомарна. Проверено сценарием S3.

### 5.5 Стоимость и длительность

`Meter` считает на задачу шаги, вызовы инструментов, токены входа и выхода (из `usage` провайдера), стоимость по ценам из конфигурации и время. В `meta.json` — итоги прогона и P50/P95 на задачу, в `runs/index.csv` — стоимость и время каждого прогона рядом с метриками. Так «до → после» в 8.3 сравнивает качество, деньги и время вместе.

### 5.6 Многошаговые сценарии

Сценарии запускаются тем же раннером (`python -m harness scenarios`), с бюджетом, инъекцией сбоев и метаданными. Тетрадь своя на каждый сценарий. Проверяется поведение, а не только «не упало».

## 6. Состояние и память

Тема memory-heavy: вся ценность — в тетради, которая живёт месяцами и обновляется. Реализация — `harness/notebook.py` (SQLite), решение об уровнях — [ADR-001](../adr/001-notebook-levels.md).

### 6.1 Какое состояние есть и где оно живёт

| Тип | Где | Что | Правило жизни | Кто пишет |
|---|---|---|---|---|
| **Рабочее состояние задачи** | `Context` в памяти процесса | шаги, бюджет, трейс, частичный результат | живёт одну задачу; после неё остаётся только в `runs/` (трейс) | оркестратор |
| **Кэш** | `l0_pages`, `extract_cache` | снимки страниц (текст, sha256, дата); результат извлечения по (sha256 страницы, хэш промпта) | неизменяемы; новая загрузка — новая строка; кэш извлечения недействителен при смене страницы или промпта | fetch, экстрактор |
| **Фактическая память** | `l1_facts` + журнал `l1_events` | атомарный факт: значение, цикл, область, источник, цитата, дата проверки, статус жизни (`active` / `retracted` / `quarantined` / `superseded`) | не удаляется и не перезаписывается; меняется только статус, с записью в журнал | валидатор после извлечения, исправления пользователя |
| **Производное** | `l2_cards`, L3 | карточка: рабочее значение + статус + альтернативы; резюме: ближайшие дедлайны и «требует внимания» | всегда пересчитывается из активных фактов L1, руками не правится | код (политика 6.5) |
| **Эпизодическая память** | `sessions`, `session_summary` | реплики диалога; резюме старых реплик | хранится до конца курса (10.3); в контекст — последние реплики + резюме **текущей** сессии | чат |
| **Состояние пользователя** | `user_lists` | избранное | переживает границу сессии (6.4), пока пользователь не удалит | пользователь |
| **Профиль** | сейчас `harness/profiles.json` (eval-профили P1, P2); в продукте — таблица профилей в той же базе | гражданство, направление, регионы | пока пользователь не удалит | пользователь |

Факты о стипендиях общие для всех пользователей (ADR-005), профиль работает как фильтр. Поэтому исправление одного пользователя — факт с источником `user:<id>`, видимый как альтернатива, а не правка общей карточки.

### 6.2 Что попадает в контекст на каждом шаге и почему

| Шаг | Контекст | Почему именно это |
|---|---|---|
| извлечение (`extract_llm`) | системный промпт + схема (~1k) + текст **одной** страницы (обрезка 60k символов; в среднем ~2,6k токенов по спайку) | одна страница — одна цитируемая единица: цитату можно проверить кодом по одному снимку; страницы разных стипендий не смешиваются |
| ответ пользователю | системный промпт + инструменты 2,5k · профиль 0,5k · L3 ≤3k · до 8 карточек L2 ≤6,5k · история ≤3k · резерв 0,5k = **≤16k** | L3 и профиль нужны почти в каждом ответе («что срочно», «подходит ли мне»), карточки — по запросу; L1 с цитатами — только для карточки в фокусе (источник, конфликт, исправление); L0 в ответ не попадает никогда |
| конфликт (U3) | две-три версии факта с цитатами из L1 + карточка | модель видит только спорные значения и их источники, а не всю страницу |

Модель ничего не помнит между вызовами: всё, что ей нужно, собирает оркестратор (`harness/context.py`).

### 6.3 Переполнение контекста

У каждого блока свой потолок, поэтому переполнение одного не вытесняет другие (`build_context`):
- **история** — режется первой и легче всего: в контекст входят готовое резюме и последние реплики по бюджету. Сценарий задаёт резюме вручную. Суть диалога (исправления, профиль) уже лежит в тетради, а не только в репликах;
- **карточки** — не больше 8. Сначала у наименее релевантных отрезаются альтернативные значения (рабочее значение, статус и источник остаются), затем такие карточки выпадают целиком. Ответ сообщает, что показаны не все;
- **L3** — обрезается до ближайших дедлайнов и блока «требует внимания»;
- **никогда не режутся** системный промпт, профиль и цитаты карточки в фокусе: без них ответ нарушает контракт провенанса. Если они не влезают в свой потолок — это ошибка конфигурации, сборка падает, а не молча режет.

Замер S7 (60 реплик, 10 найденных карточек): обычный бюджет — 7347 оценочных токенов, карточек: 8, история урезана до последних реплик + резюме. Урезанный бюджет (карточки 1,5k, история 0,8k, L3 0,4k) — 4694 оценочных токенов, карточек: 6, системный промпт и цитаты в фокусе на месте. Токены оцениваются как 4 символа на токен; для стоимости используются реальные `usage` провайдера.

### 6.4 Где состояние живёт между запросами

В прототипе КТ3 данные тетради и сессии живут в SQLite `:memory:` между операциями одного сценария. Между сценариями создаётся новая база для изоляции прогонов. Профили читаются из `harness/profiles.json`. Для продукта запланирована файловая SQLite с сохранением между запросами.

**Граница сессии.** Сессия — один разговор, у неё свой `session_id`. Новая сессия начинается по команде «новый разговор» или после 24 ч без реплик; в eval её задаёт маркер «[новая сессия …]» в реплике (q091). Через границу переходит состояние пользователя: избранное (`user_lists`), профиль и исправления (факты L1 с источником `user:<id>`). Реплики и резюме прошлой сессии в контекст новой не попадают, рабочее состояние задач не хранится. Проверено в S5: в новой сессии реплик прошлой нет, а избранное и исправление на месте. Рабочее состояние задачи между запросами не хранится, и это решение. Задача — это одна операция (ответ, загрузка стипендии, перепроверка), всё её значимое сохраняется в L1 атомарно в конце. Незаконченную задачу дешевле перезапустить: L0 и кэш извлечения делают повтор почти бесплатным. Продолжать с середины не нужно.

### 6.5 Противоречия: новый факт против записанного

Новый факт **никогда не перезаписывает** старый: оба остаются в L1. Рабочее значение карточки выбирает код по правилам:
1. `retracted` / `quarantined` / `superseded` не участвуют, но остаются в L1 и журнале;
2. более новый цикл важнее старого (прошлогодний снимок не перебивает текущий);
3. в одном цикле: официальный источник / вуз > пользователь > агрегатор > прошлогодний снимок;
4. **исключение для дедлайнов:** если в одном цикле расходятся официальный источник и пользователь, рабочим становится **более ранняя дата**. Ошибка «дата позже реальной» критична (1.2), ранняя дата безопаснее. Так закрыт открытый вопрос «что выше: исправление пользователя или официальная страница»: ни то ни другое, выбирается более ранняя дата;
5. любое расхождение в выбранном цикле → статус `конфликт`, в ответе показываются все значения с источниками и датами, карточка попадает в «требует внимания».

**След:** каждое изменение статуса факта — строка в `l1_events` (кто, когда, почему). Повтор той же записи фиксируется как `duplicate_ignored`. Проверено S4 и S5.

### 6.6 Устаревание

У каждого факта есть `checked_at` — дата загрузки снимка, из которого он извлечён (для исправления — дата исправления). При недоступном сайте дата **не освежается** задним числом (S2). Рабочее значение получает статус `устарел`, если:
- оно относится к прошлому циклу, или
- `checked_at` старше 14 дней, а для дедлайнов ближе 30 дней — старше 72 часов (свежесть, 2.1, M11).

`устарел` — сигнал планировщику перепроверить: fetch, сравнение sha256 текста с L0 (2.1, 4), при изменении — новое извлечение, затем пересчёт L2.

### 6.7 Отравление памяти

Тест — сценарий S6, три пути:

| Путь | Что сделали | Распространилось? | Как вычищается |
|---|---|---|---|
| неверный факт записан прямо в L1 (баг, ручная правка базы) | Lund: «16 February **2027**», цикл 2027/28, источник «официальный», цитаты в снимке нет | **да**: карточка и L3 показали подтверждённый дедлайн 2027 вместо прошлого цикла. Это ожидаемо — L2/L3 производные и доверяют L1 | **аудит L1 по L0** (`Notebook.audit`): факт, цитата которого не найдена в снимке, уходит в карантин. Карточка и L3 пересчитываются и возвращаются к правде, в журнале — `insert → quarantined` с причиной |
| неверный факт через извлечение (галлюцинация модели) | экстрактор вернул дату с выдуманной цитатой | **нет**: валидатор отклонил факт до записи в L1 | не требуется |
| пользователь называет неверную дату | «дедлайн Eiffel 1 марта» (официально 6 января) | **частично**: виден как альтернатива, карточка в статусе `конфликт` | рабочее значение остаётся ранним официальным (правило 4); пользователь или команда отменяет исправление (`undo_correction`) |

**Что тест не ловит.** Неверная интерпретация, у которой есть настоящая цитата: например, дата открытия приёма, извлечённая как дедлайн подачи. Аудит по L0 её не найдёт, потому что цитата подлинная. Смягчение: тип даты в схеме, ловушки в eval (M4), перепроверка более сильной моделью при конфликте (U3), исправления пользователей.

### 7.1 Устройство: две части

Система делает две разные вещи, и проверять их нужно по-разному:

Снимки страниц нужны для воспроизводимости: сайты меняются, и к декабрю живые страницы разойдутся с эталоном. Офлайн на снимках считаются M4, M5, M6, M8 и все метрики части B; вживую, с фиксацией даты прогона, — только M1 (покрытие) и M3 (релевантность найденного).

**Почему такие доли.** Факты и время (56 из 120) — ядро контракта и самая дорогая ошибка (дедлайн). Каждая исключительная категория — не меньше 8 примеров, чтобы давать сигнал.

**Откуда запросы.** Реальных пользователей пока нет. Запросы составлены по сценариям 2.2 и ловушкам, найденным в спайке; 20 запросов КТ1 вошли в набор. Чтобы набор не состоял из одинаково «гладких» формулировок, 20 видимых запросов переформулированы в стиле живого пользователя (небрежно, с опечатками, транслитом, смесью языков, контекстом о себе) отдельным LLM-агентом на другой модели (Sonnet), без доступа к эталону. Каждая переформулировка проверена на сохранение сущностей, дат и условий, чтобы эталонный ответ оставался верным; исходный текст сохранён в поле `original_turns`, у запроса — пометка `paraphrased_llm`. Реальных формулировок пользователей пока нет — это записано в рисках.

**Пополнение из прода.** Ошибки, 👎 и ручные исправления пользователей попадают в кандидаты следующей версии набора (v2), не в v1.

**Итог части B.** 120 запросов (`eval/queries/visible.jsonl` + отложенная часть), дата eval зафиксирована — 25.10.2026 (от неё считаются «ближайшие 30 дней» и «что уже закрылось»). Эталонные факты не дублируются в запросах: запрос ссылается на id меток A2 и пар A3, в нём — только ожидаемое поведение (`answer` / `not_found` / `refuse` / `boundary`) и критерии «обязательно» / «недопустимо». Видимых 81, отложенных 39. Перекос: в discovery отложено 8 из 12 — широкие запросы почти всегда затрагивают хотя бы одну отложенную стипендию; discovery дополнительно проверяется вживую по M1 на всём A1.

### 7.4 Процедура получения ground truth

1. **Снимки.** Скрипт `eval/scripts/snapshot.py` сохраняет текст каждой страницы (trafilatura), sha256 и дату загрузки. Размечается только снимок, не живая страница.
2. **Разметчик A — LLM-агент** (Claude в Claude Code) по инструкции `docs/annotation_guide.md`. Каждое значение — с дословной цитатой из снимка и URL; если значения нет на странице — явно `null` с пометкой «нет на странице».
3. **Автоматическая проверка** (`eval/scripts/validate.py`): схема, формат дат, каждая цитата буквально есть в снимке.
4. **Двойная разметка.** 30 стипендий видимой части A2 независимо размечает **разметчик B — LLM-агент второго участника команды** (отдельная сессия, только инструкция и снимки, без доступа к меткам A). Промпт — `docs/annotator_b_prompt.md`.
5. **Согласие** (`eval/scripts/agreement.py`):
   - дедлайн подачи (дата + точность + область) — доля полного совпадения, цель ≥90 %;
   - статус цикла, `open_to_ru` — κ Коэна, цель ≥0,8;
   - основная выплата (сумма + валюта + период) — доля совпадения, цель ≥85 %.

   Если ниже цели — уточняем инструкцию и переразмечаем расхождения. Посчитанное согласие — потолок M4 и M5: точнее эталона систему не измерить.
6. **Проверка человеком.** Участник команды проверяет по цитатам все расхождения A и B и 20 случайных меток A (`eval/review/labels_check.md`). Знание предметной области не требуется: открыть снимок, найти цитату, сверить значение. **Выполнено:** 26 стипендий проверены, ошибок не найдено.
7. **Итоговый эталон** — метки A после разбора расхождений; все исправления логируются в `eval/gt/adjudication.md`.

**Результат (25.10.2026, 30 стипендий):** дедлайны подачи — 97 % полного совпадения, основная выплата — 93 %, статус цикла — κ = 1,00, `open_to_ru` — κ = 0,84; все выше целей. Из 6 расхождений в 3 прав B (A был излишне осторожен в `open_to_ru`; после этого перепроверены все `unknown` и исправлены ещё 2 метки), в 3 — A (инструкция уточнена). Потолок M4 ≈ 97 %, M5 ≈ 93 %.

**Ограничение.** Эталон размечен LLM. Если система будет работать на модели того же семейства, ошибки могут коррелировать. Смягчение: цитаты (метка проверяема), проверка человеком, сравнение провайдеров в ADR-004.

### 7.5 Видимая и отложенная части

- **Единица разбиения — стипендия**, а не запрос: все запросы B и пары A3/A4 про отложенную стипендию уходят в отложенную часть. Иначе — утечка.
- A2: **70 видимых / 30 отложенных**, стратифицированно по странам и типам ловушек. Запросы B, не привязанные к стипендиям (вне домена, несуществующие), — 70/30 случайно по категориям.
- Стипендии, на которых делался спайк (`docs/spike_kt2.md`, 15 страниц), — примеры разработки: только в видимой части, в отложенную не попадают.
- Отложенная часть (30 меток A2, 39 запросов B, 9 пар A4) хранится одним зашифрованным пакетом (`eval/heldout/heldout.enc`), ключ — вне репозитория; в git — sha256 открытого файла (`eval/heldout/SHA256`). **Не открывается до КТ4**; на КТ4 хэш подтверждает, что файл не менялся. В `reference_list.csv` поля `in_profile` и `open_to_ru` отложенных стипендий скрыты (`heldout`).
- **Риск утечки через разработчика.** Разметчик A — тот же агент, что помогает писать код. Правило: метки отложенной части не используются в промптах, few-shot примерах и правилах; промпты и правила отлаживаются только на видимой части.

**Чем eval отличается от данных разработки.** На видимой части отлаживаются промпты и правила; отложенная проверяет обобщение на новых стипендиях и страницах той же стратификации. Примеры спайка — отдельный набор для разработки, в метриках не участвуют.

### 7.6 Процедура прогона

- **Офлайн** (воспроизводимо): извлечение по снимкам A2 → M4, M5, M6, M8(а); запросы B к тетради, собранной из снимков видимой части → M4–M9. **Вживую:** discovery по профилю → M1; ручная проверка выборки найденного → M3.
- **Когда:** smoke — 20 запросов-ловушек (canary) на каждый PR, меняющий промпты или извлечение; полный прогон видимой части — на каждой КТ и перед сменой модели; отложенная часть — только на КТ4.
- **Повторы:** ответы при temperature > 0 — 3 прогона, отчитываемся средним и минимумом; извлечение — 1 прогон + 3 повтора на 20 страницах для оценки разброса.
- **Регрессия:** падение любой метрики >3 п.п. относительно предыдущего прогона или хотя бы одна опасная ошибка на canary — изменение не мержится до полного прогона.
- **Артефакты прогона** сохраняются вместе с метаданными: версия модели, хэш промптов, temperature/seed, версия eval-набора, дата, стоимость, длительность.

## 8. Baseline и план усложнений

### 8.1 Baseline (не LLM)

**B1 «поиск + правила»** — основной baseline, запускается тем же харнессом и на тех же данных, что система:
- discovery: те же запросы в Tavily, топ-10, дедупликация по домену и нормализованному названию; записью считается любой результат с официального домена;
- факты: регулярные выражения по тексту страницы — первая дата рядом со словами `deadline|closing date|apply by`, сумма рядом с `per month|per year|monthly`; статус цикла — по году найденной даты;
- ответы на запросы B — шаблон: найденные ссылки + извлечённые значения;
- конфликты, исправления и память не поддерживаются: по M7 и M9 — честный 0.

Прогноз на КТ2 («где B1 заведомо ошибётся») против факта прогона на КТ3:

|---|---|
| Chevening — дедлайн оффера 8 July 2027 вместо подачи | взял «20 October» без года с другого места страницы → цикл неизвестен, статус `not_found` (в эталоне — октябрь 2026 по странам) |

**Как читать M4.** Исходы разделены (3.1). У 32 из 70 стипендий дедлайна подачи на страницах нет, и здесь обе системы в основном правы — просто не найдя дату. Слабость видна на стипендиях с датами: B1 — 10 из 38, шаг 1 — 14–17 из 38. *(В версии 0.3 до ревью было написано «41 стипендия без дат»: туда попали и 9 стипендий, где дата есть, а цикл неизвестен.)*

**Решение по шагу 1: порог не пройден.** Условие перехода (8.2): M4 выше B1 на ≥20 п.п. и опасных ≤3 на 100. Факт: +10 п.п., опасных 3,3 на 100. M5 вырос сильнее (+23 п.п.), но шаг 2 по плану не начинаем, шаг 1 дорабатываем. Разбор ошибок M4 за 3 повтора (80 ошибочных решений из 210; 17 стипендий ошибочны во всех трёх повторах, 20 — в части):
- **лишние даты — 30:** модель записывает в дедлайны подачи раунды, даты программ и окна приёма, которых нет в эталоне. Чиним промптом: определение `application`, пример «окно подачи на магистратуру ≠ дедлайн стипендии, если она не подаётся вместе с программой»;
- **те же даты, другая область или точность — 23:** `global` вместо `program` / `applicant_group`, день вместо месяца. Чиним промптом и схемой (`scope_detail` обязателен при не-global);
- **дата там, где в эталоне её нет — 12;** из них опасные (выдуманный дедлайн): Oulu (во всех 3 повторах — окно подачи на магистратуру 21.01.2027 записано как дедлайн стипендии; метка спорная, см. ниже), Glasgow («usually in late August» → 2027-08), Manchester (начало обучения 2027-09 → дедлайн);
- **статус цикла — 10:** даты верные, цикл не тот или не указан;
- **другие даты или пропущенные — 5.**

**M8(в) = 83 %: настоящая цитата, неверное значение.** Проверяющий — LLM-агент на Claude, экстрактор — `gpt-5.4-mini`. Эталон агент не видел, только снимки. Из 30 фактов в 5 цитата есть в снимке, но не подтверждает значение:
- Paris-Saclay: дата отбора координаторами выдана за дедлайн подачи, область `program` вместо общей;
- Zuse RelAI: дедлайн PhD-набора выдан за общий;
- Umeå: дедлайн весеннего семестра (только отдельные курсы) — за дедлайн магистратуры;
- KU Leuven: цикл 2026/27 взят из шапки страницы, хотя подача в 2026–2027 гг. идёт на 2027/28;
- Radboud: оставшаяся плата за обучение €2 771 выдана за выплату.

Это ровно тот класс ошибок, о котором предупреждало ревью: M8(а) = 0 %, а M8(в) его ловит. Те же правки промпта (тип даты, область, «сумма — выплата, а не остаток платы») проверяются и по M8(в).

**Спорная метка.** Oulu: инструкция разметки считает дедлайн программы дедлайном стипендии, если стипендия подаётся вместе с программой. Разметчик решил, что отдельной подачи нет («скидка для принятых»). Eval v1 заморожен, метку не меняем; вопрос — в разбор для v2.

**Что дальше по шагу 1** (до шага 2, КТ4): правка промпта по разбору выше → тот же прогон ×3 → тот же порог. Затем шаг 6 досрочно: 2–3 модели на тех же 70 стипендиях. Прогон стоит $0,4, поэтому сравнение моделей укладывается в бюджет.
