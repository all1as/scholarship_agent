## 1. Контекст

### 1.1 Бизнес-задача
**Проблема.** Абитуриент (магистратура STEM/IT: ЕС, UK, США, Канада) 4–6 мес. собирает стипендии. Вручную находит 20–40 из сотен релевантных; агрегаторы устаревают и расходятся с официальными сайтами; таблица теряет источники и даты. Ошибка в дедлайне = потерянный год.

**Почему LLM-система.** Агрегаторы не фильтруют по профилю и не показывают источник/дату; скрейперы ломаются на разнородных страницах, условия написаны свободным текстом; разовый чат или deep research не хранит состояние и не отслеживает изменения.

**Альтернативы без системы** (на 3 мес, база ~150–200 стипендий):

| Альтернатива | Стоимость | Минус |
|---|---|---|
| Вручную + Excel | ≈75 ч: старт 150 × 20 мин ≈ 50 ч + ~12 ч/мес перепроверок | на практике до такого объёма никто не доходит, база устаревает |
| Только агрегаторы | 0, ~10–15 ч | старые даты, нет фильтра и учёта; часть дат противоречит официальным (см. `docs/spike_kt2.md`) |
| Консультант | [собрать цены, см. 11] | дорого, узкий охват |
| **Система** | ≈ $8 старт + ≈ $7/мес (3.3) | — |

**Успех для пользователя:** найдено ≥2× больше релевантных стипендий, чем вручную (≥150 записей с официальным источником, покрытие ≥70 % эталонного списка); ≤2 ч/мес времени пользователя; 0 пропущенных дедлайнов из-за неверной даты; у каждого факта есть источник и дата.

### 1.2 Пользователи и нагрузка
- **Кто:** русскоязычные студенты 3–4 курса бакалавриата и выпускники, поступающие в зарубежную магистратуру по STEM/IT (ЕС, UK, США, Канада). Готовят заявки 4–6 мес., рассматривают 10–30 программ, часть стипендий требует отдельной подачи.
- **Масштаб MVP:** до 4 профилей (2 разработчика с реальными профилями + до 2 проверяющих); одна общая база (факты о стипендиях не персональны), профиль работает как фильтр.
- **Канал:** чат (Telegram или веб) + фоновые запуски по расписанию; экспорт в CSV.
- **Нагрузка в месяц** (уменьшена в v0.2: учебный проект, бюджет на API минимальный):
  - старт: ~400 лидов (названий из поиска) → ~250 кандидатов с официальной страницей → ~150 записей;
  - далее: ~100 лидов → ~60 кандидатов; ~900 загрузок страниц для перепроверки, из них ~135 изменились и идут в модель;
  - ~150 вопросов от пользователей + eval: 2 полных прогона (100 страниц + 120 запросов) и 4 smoke-прогона по 20 запросов;
  - пик в ноябре–январе.
- **Цена ошибки:**
  - дедлайн показан позже реального или прошлогодний выдан за текущий — **критично**;
  - неверная eligibility (10–20 ч на заявку впустую) — **высокая**;
  - стипендия не найдена — **высокая**;
  - неверная сумма — **средняя**.

### 1.3 Границы и допущения

| Внутри | Снаружи (не гарантируем) |
|---|---|
| тетрадь, правила подъёма фактов и разрешения конфликтов, профили, оркестратор, планировщик, eval | сайты фондов и агрегаторов, поисковый API, LLM-провайдер, решения комиссий |

**Не делаем:** подачу заявок, письма и CV, оценку шансов, визовые и юридические вопросы, PhD и бакалавриат.

**Допущения** (✔ — проверено в спайке `docs/spike_kt2.md`):
- у ≥80 % стипендий есть официальная страница с дедлайном — ✔ частично: дедлайн часто на подстранице или на странице страны;
- за месяц меняется ~15 % страниц — не проверено, измерим по логам перепроверки (КТ3);
- снапшоты 2024–2026 доступны в Wayback Machine — ✔ (запросы последовательно);
- доступ к API с оплатой есть — ✔ Tavily (бесплатный тариф), OpenAI для тестов; провайдер выбирается в ADR-004;
- robots.txt и ToS позволяют читать страницы — ✔ для официальных сайтов из выборки; 2 из 3 агрегаторов блокируют ботов;
- пользователь один раз заполняет профиль;
- заметная часть стипендий может быть закрыта для граждан РФ — проверяется при разметке (поле `open_to_ru`).

## 2. Контракт

M1–M11 — идентификаторы метрик из 3.1; на них ссылаются контракт, SLO и eval-сет. Изменения v0.2 по итогам спайка (`docs/spike_kt2.md`) отмечены в «Истории изменений».

### 2.1 Контракт

| Поле | Обещание | Метрика |
|---|---|---|
| Вход | Вопросы и команды на RU/EN о стипендиях на магистратуру в рамках профиля («найди ещё», «дедлайн X», «покажи расхождения», «исправь»). Остальное — отказ. | M8 |
| Покрытие | Discovery по профилю находит ≥70 % стипендий из эталонного списка к защите (≥50 % к КТ3). | M1 |
| Выход | Каждый факт = значение + URL + дата проверки + статус (`подтверждён` / `вероятен` / `конфликт` / `устарел`) + дословная цитата из источника. | M6, M8 |
| Дедлайн | Дедлайн подачи = дата + точность (день / месяц) + цикл (intake 2027) + область (общий / страна / вуз / программа / группа заявителей). Дату оффера, результатов или открытия приёма не выдаём за дедлайн подачи. Если дедлайн задаётся по стране или вузу — показываем значение для профиля, а если его нет в тетради — явно «зависит от …» со ссылкой. | M4 |
| Сумма | Основная выплата (сумма, валюта, период) или признак полного покрытия; бюджет программы целиком не выдаётся за выплату. | M5 |
| Противоречия | Не затираются, оба значения хранятся. Приоритет: официальный > университет > агрегатор; новый цикл > старый. Официальный источник старее и расходится → `конфликт`, показываем оба. | M7 |
| Новая запись | Нужны: официальная страница (фонд, вуз, госорган); известны фонд или вуз; пройдены фильтры (магистратура, направление, гражданство не исключено, цикл ≥ текущего). Агрегаторы и блоги — только источник названий («лиды») и пополнение «кандидатов». | M3, M10 |
| Статус цикла | Вычисляется кодом по извлечённым датам, а не моделью: `подтверждён` — есть дедлайн подачи цикла 2027; `устарел` — только прошлый цикл; `не подтверждено` — дат нет. | M4 |
| Неуверенность | «Не подтверждено для цикла 2027» + ссылка; дедлайн не выдумывается и не переносится из прошлого цикла. | M4, M8 |
| Исправление пользователя | Пишется как факт с источником «пользователь, дата» и участвует в политике конфликтов; все следующие ответы его учитывают. | M9 |
| Не обещаем | полноту сверх целевого покрытия, итоговое решение по eligibility, шансы, юридическую силу | дисклеймер |
| Нефункциональные | чат: TTFT ≤2 с, e2e ≤15 с (P95); перепроверка ≤90 с; свежесть ≤14 дней, для дедлайнов ≤30 дней — ≤72 ч | 3.2, M11 |

### 2.2 Сценарии

| Сценарий | Пример | Результат |
|---|---|---|
| Discovery | «Найди стипендии по CS в Германии» | +N записей, M в кандидатах (с причиной) |
| Факт | «Дедлайн Eiffel на 2027?» | дата + цикл + область + ссылка + статус |
| Дедлайн по стране | «Дедлайн Chevening?» | «октябрь 2026, точная дата — на странице страны» + ссылка; дата оффера не выдаётся за дедлайн |
| Срочное | «Что закрывается за 30 дней?» | отсортированный список |
| Конфликт | «Почему дата не как на агрегаторе?» | оба значения, источники, правило выбора |
| Исправление | «Дедлайн 1 ноября, я звонил» | сохранено, конфликт с официальным виден |
| Перепроверка | «Проверь Holland сейчас» | diff с тетрадью |

| Исключение | Поведение |
|---|---|
| факта нет | `не найдено`, ссылка на официальную страницу |
| только прошлый цикл | `устарел`, цикл указан явно |
| дедлайн без года на странице | год не достраивается; дата хранится с точностью «день, год неизвестен» и статусом `вероятен`, пока цикл не подтверждён контекстом страницы |
| сайт блокирует бота (403) или отдаёт JS-оболочку | Tavily Extract как запасной путь; если и он не смог — запись остаётся в «кандидатах» с причиной |
| несуществующая стипендия | «не найдено», 0 записей |
| вне домена | отказ по контракту |
| сайт / API недоступен | 2 ретрая, показ последнего значения с датой |
| невалидный JSON | 1 повтор, затем в кандидаты с флагом |
| зацикливание агента | лимит шагов и бюджета, частичный отчёт |
| эскалация | оператора нет; `конфликт` и `не подтверждено` у ближайших дедлайнов идут в блок «требует внимания» |

### 2.3 Диалог и память
- **Режим:** multi-turn.
- **История:** последние ~10 реплик, ≤3k токенов, старое сворачивается в резюме.
- **Где живёт память:** в хранилище (тетрадь L0–L3 + профили + журнал сессий). Что подгружать, решает оркестратор; модель сама ничего не помнит.
- **Профиль:** хранится с согласия, его можно посмотреть и удалить.
- **Тон:** русский, коротко, сначала ответ, потом источники, без обещаний шансов.
- **Прозрачность:** пользователь знает, что это бот; у каждого факта видна дата проверки.

## 3. Бюджеты и SLO

### 3.1 Качество
Эталон (GT), состав eval-сета и процедура разметки — в разделе 7. Здесь — метрики и пороги.

| ID | Метрика | Пункт контракта | Как считаем | Цель | Откат |
|---|---|---|---|---|---|
| M1 | Покрытие | Покрытие | доля эталонного списка (раздел 7, часть A1), найденная discovery по профилю; прогон вживую, дата фиксируется | ≥50 % к КТ3, ≥70 % к защите | <40 % |
| M2 | — | — | **исключена в v0.2**: объём не является обещанием контракта и раздувается гранулярностью записей; ориентир объёма остаётся в 1.2 | — | — |
| M3 | Релевантность | Новая запись | доля записей, прошедших фильтры профиля, по ручной проверке случайной выборки 50 записей | ≥85 % | <75 % |
| M4 | Дедлайн | Дедлайн, Статус цикла, Неуверенность | **по каждой стипендии A2 (100 решений)**: верны статус цикла (`подтверждён` / `устарел` / `не подтверждено`) и множество дедлайнов подачи (дата, точность, область). **Опасная ошибка** — дата позже реальной, дата прошлого цикла выдана за текущую или выдуман дедлайн там, где в эталоне его нет | ≥90 %; опасных ≤1 на 100 стипендий | опасных >3 на 100 |
| M5 | Сумма | Сумма | совпадение основной выплаты (сумма + валюта + период) или признака полного покрытия с A2 | ≥80 % | <70 % |
| M6 | Провенанс | Выход | у факта есть URL, дата проверки, статус и цитата; проверка схемой | 100 % | <98 % |
| M7 | Конфликты | Противоречия | на парах A3: верно выбрано / оба значения показаны / тихие перезаписи | ≥90 % / ≥95 % / 0 | <80 % / <90 % / >0 |
| M8 | Выдумки и отказы | Выход, Вход, Неуверенность | (а) доля фактов, цитата которых не найдена в снимке страницы (L0) — правило в коде, без judge; (б) на несуществующих стипендиях и запросах вне домена — «не найдено» / отказ и 0 новых записей | (а) ≤2 %; (б) 100 % | (а) >5 %; (б) <95 % |
| M9 | Исправления | Исправление пользователя | многоходовые сценарии B: после исправления 5 контрольных вопросов учитывают его | 100 % | <100 % |
| M10 | Дубли | Новая запись | на парах A4 (алиасы и похожие, но разные стипендии): доля склеенных разных + не склеенных одинаковых | ≤3 % | >7 % |
| M11 | Свежесть | Нефункциональные | дедлайны ≤30 дней перепроверены за 72 ч — **SLO по телеметрии** (КТ4), на фиксированном наборе не считается | ≥95 % | <85 % |

**Почему M4 считается по стипендиям и почему опасные — «на 100».** Разметка показала: у 50 из 100 стипендий на официальных страницах вообще нет дедлайна подачи, у 29 есть дедлайн цикла 2027/28 (всего 69 дедлайнов). Считать по дедлайнам — значит не проверять самый частый случай «дат нет», где опасная ошибка — выдумать дату. Поэтому единица M4 — стипендия: 100 решений. На такой выборке 0 и 1 % статистически не различимы: при 0 ошибках верхняя граница 95 % доверительного интервала ≈3 % (правило трёх). Поэтому цель — не больше одной опасной ошибки, а откат — только при явной проблеме (>3), а не при первой же ошибке.

**Бюджет контекста.** Тетрадь в ~10 раз больше окна модели (200k), поэтому нужна иерархия.

Объём тетради к защите (~200 записей, ~3 страницы на запись):

| Уровень | Что лежит | Объём | Попадает в промпт |
|---|---|---|---|
| L0 | снимки страниц (текст после trafilatura + хэш + дата) | ≈1,8M токенов | только при переизвлечении |
| L1 | атомарные факты с цитатами и источниками | ≈0,5M | по запросу (источник, конфликт) |
| L2 | карточки стипендий | ≈160k | до 8 карточек через retrieval |
| L3 | резюме: профиль, топ, ближайшие дедлайны | ≤3k | всегда |

Лимит на один ответ — **≤16k входных токенов**: системный промпт + инструменты 2,5k, профиль 0,5k, L3 ≤3k, карточки ≤6,5k, история ≤3k.

### 3.2 Задержка

| Этап (ответ по тетради) | мс |
|---|---|
| сеть + шлюз | 50–100 |
| retrieval (SQLite FTS / вектора) | 50–150 |
| prefill ~12k (TTFT, API) | 500–1500 |
| decode 600 ток × 10–15 мс | 6000–9000 |
| шагов | 1–2 |
| **e2e P50 / P95** | **~7 с / ~13 с** |

Цели:
- **чат:** TTFT P95 ≤2 с, e2e P95 ≤15 с, стриминг включён;
- **перепроверка «сейчас»:** ≈20–30 с, P95 ≤90 с;
- **фоновый discovery:** ~25 с на кандидата (основная страница + 1–3 подстраницы; извлечение одной страницы в спайке — 1,3–5 с); стартовые 250 кандидатов при параллелизме 10 ≈ 10 мин, цель ≤1 ч;
- **Batch API** (до 24 ч) допустим для фона и eval, кроме дедлайнов ≤72 ч.

### 3.3 Стоимость
Провайдер ещё не выбран (сравнение — ADR-004, КТ3). Ниже расчёт по ценам Claude как референс; для тестов в спайке использовался `gpt-5.4-mini`, после выбора провайдера таблица пересчитывается по тем же объёмам.

Цены на 04.10.2026:
- Haiku 4.5 — $1 / $5 за 1M токенов; Sonnet — $3 / $15;
- чтение из кэша — 10 % цены входа; Batch API −50 %;
- Tavily: 1000 бесплатных кредитов/мес. Расход ≈340 в первый месяц (≈60 широких поисков + ≈250 поисков официальных страниц + extract) и ≈150 потом — укладывается, поэтому ниже считается только LLM.

**Что снижает стоимость:**
- discovery в два шага: из широкой выдачи берутся только названия, модель читает только официальные страницы;
- отсев лидов по сниппету до загрузки страниц;
- перепроверка: fetch + сравнение хэша текста бесплатно, модель вызывается только при изменении (~15 % страниц);
- статус цикла, даты «через N дней», фильтры — в коде, без модели;
- M8 считается правилом (цитата есть в L0), без judge;
- eval извлечения — на сохранённых снимках страниц, без повторного поиска;
- кэш системного промпта и L3 в ответах; batch для фона и eval.

- **Бюджет:** ≤ $10 старт, ≤ $8/мес, ≤ $25 на проект + резерв $10 на отладку (повторные прогоны, эксперименты с промптами) → выбираем B. Переход на C — если ответы дешёвой модели не держат M4/M7 (ADR-004).
- **Драйверы стоимости:** месяц 1 — извлечение кандидатов и L3; далее — eval и L3.
- **Скрытые затраты:** эталон размечает LLM-агент (раздел 7.4) — время команды ≈3–4 ч на проверку меток и спорных случаев; ручная проверка релевантности (M3) ≈1 ч на прогон.
- **Self-host:** не рассматриваем — данные публичные, нагрузка мала.

### 3.4 Компромисс
Главное — точность дедлайнов (M4) и покрытие (M1). Стоимость — жёсткое ограничение ($8/мес, $25 на проект): это учебный проект, поэтому масштаб базы уменьшен до ~150–200 записей — для eval и демо этого достаточно, методика оценки от масштаба не зависит. Задержка вторична: тяжёлая работа идёт в фоне. Массовые операции — на дешёвой модели через batch; сильная модель — там, где ошибка тиражируется (конфликты, L3). При нехватке бюджета режем discovery и частоту полных eval, но не перепроверку ближайших дедлайнов. Принимаем более низкую M5 на «хвосте» малых университетских стипендий.

## 4. Архитектура (набросок)

```
[чат] → [шлюз: бюджет, учёт токенов] → [оркестратор] ← [планировщик: discovery / перепроверка / резюме]
                                            ↓ ↑
                         [LLM API: дешёвая / сильная модель, ADR-004]
                                            ↕
  [тетрадь, общая база]                               [инструменты]
   L0 сырые выписки (неизменяемые, с хэшем)            web search, fetch/extract,
   L1 факты: значение+источник+дата+статус             CRUD тетради, текущая дата
   L2 карточки: разрешённые значения + конфликты
   L3 резюме на профиль: топ, ближайшие дедлайны
   + профили, журнал сессий, кандидаты
  ─────────────── наблюдаемость: трейсы, стоимость, eval (Langfuse) ───────────────
```

| Блок | Готовое | Пишем сами |
|---|---|---|
| Клиент | Telegram Bot API / Streamlit | карточка стипендии |
| Шлюз | LiteLLM / OpenRouter | лимит бюджета системы |
| Оркестратор | PydanticAI / LangGraph | подъём фактов, политика конфликтов, правило заведения |
| Хранилище | SQLite (+ FTS / вектора) | схема L0–L3 |
| Инструменты | Tavily / Brave, trafilatura | дедупликация, сравнение хэшей |
| Наблюдаемость | Langfuse | eval-харнесс на GT |

**Путь вопроса:** L3 + профиль → retrieval до 8 карточек L2 → L1 только для источника, конфликта или исправления → валидация (у каждого факта источник, дата, статус) → стриминг. L0 читается только при переизвлечении.

**Путь discovery** (два шага — по итогам спайка: на широких запросах официальные сайты дают 30 % выдачи и ни разу не в топ-3):
1. широкий поиск (Tavily, `exclude_domains` для соцсетей) → из выдачи берутся только названия стипендий (лиды) → отсев по сниппету;
2. для каждого лида — поиск официальной страницы (запрос по названию, `include_domains` по домену фонда, если он известен) → загрузка основной страницы и подстраниц `timeline|dates|deadline|apply|eligibility` на 1 уровень → L0;
3. L0 → извлечение в L1 (JSON-схема, цитата у каждого значения) → валидатор → правило заведения → дедупликация → L2 → L3 помечается устаревшим и пересобирается.

**Получение текста страницы:** свой fetch (`httpx`, честный User-Agent, robots.txt) + `trafilatura`; Tavily Extract — запасной путь для 403 и JS-оболочек. Подмену User-Agent не используем. Выбор фиксируется в ADR-006.

**Модель данных дедлайна:** `date` (YYYY-MM-DD или YYYY-MM), `granularity` (day / month), `type` (application / offer_or_documents / results / opening / other), `scope` (global / country / university / program / applicant_group) + `scope_detail`, `cycle`, `quote`, `source_url`. У одной стипендии может быть много дедлайнов (Chevening и DAAD — по странам, NL Scholarship и Gates — по вузу или курсу).

**Валидатор после извлечения (код, не модель):** формат даты; цитата буквально есть в L0; статус цикла вычисляется по датам (раздел 2.1); дата открытия приёма не может быть единственным дедлайном подачи. Ошибки спайка, которые он ловит: дата «20 October» без года, статус `подтверждён` без дат (Rhodes, DAAD).

**Путь перепроверки:** fetch → сравнение хэша основного текста с L0 (хэш сырого HTML нестабилен) → если изменилось, новое извлечение в L1 → пересчёт L2.

**Подъём L1→L2:** карточка всегда пересчитывается из L1, поэтому исправление доходит до всех ответов (M9).

**Baseline и план усложнений** — раздел 8.

**ADR:**
- 001 — уровни тетради и подъём факта;
- 002 — политика противоречий;
- 003 — право завести запись;
- 004 — модели и роутинг (сравнение провайдеров на видимой части eval, КТ3);
- 005 — общая база + профиль как фильтр;
- 006 — получение текста страниц: свой fetch vs Tavily Extract.

### 7.1 Устройство: две части

Система делает две разные вещи, и проверять их нужно по-разному:

### 7.4 Процедура получения ground truth

1. **Снимки.** Скрипт `eval/scripts/snapshot.py` сохраняет текст каждой страницы (trafilatura), sha256 и дату загрузки. Размечается только снимок, не живая страница.
2. **Разметчик A — LLM-агент** (Claude в Claude Code) по инструкции `docs/annotation_guide.md`. Каждое значение — с дословной цитатой из снимка и URL; если значения нет на странице — явно `null` с пометкой «нет на странице».
3. **Автоматическая проверка** (`eval/scripts/validate.py`): схема, формат дат, каждая цитата буквально есть в снимке.
4. **Двойная разметка.** 30 стипендий видимой части A2 независимо размечает **разметчик B — LLM-агент второго участника команды** (отдельная сессия, только инструкция и снимки, без доступа к меткам A). Промпт — `docs/annotator_b_prompt.md`.
5. **Согласие** (`eval/scripts/agreement.py`):
   - дедлайн подачи (дата + точность + область) — доля полного совпадения, цель ≥90 %;
   - статус цикла, `open_to_ru` — κ Коэна, цель ≥0,8;
   - основная выплата (сумма + валюта + период) — доля совпадения, цель ≥85 %.

   Если ниже цели — уточняем инструкцию и переразмечаем расхождения. Посчитанное согласие — потолок M4 и M5: точнее эталона систему не измерить.
6. **Проверка человеком.** Участник команды проверяет по цитатам все расхождения A и B и 20 случайных меток A (`eval/review/labels_check.md`). Знание предметной области не требуется: открыть снимок, найти цитату, сверить значение. **Выполнено:** 26 стипендий проверены, ошибок не найдено.
7. **Итоговый эталон** — метки A после разбора расхождений; все исправления логируются в `eval/gt/adjudication.md`.

**Результат (25.10.2026, 30 стипендий):** дедлайны подачи — 97 % полного совпадения, основная выплата — 93 %, статус цикла — κ = 1,00, `open_to_ru` — κ = 0,84; все выше целей. Из 6 расхождений в 3 прав B (A был излишне осторожен в `open_to_ru`; после этого перепроверены все `unknown` и исправлены ещё 2 метки), в 3 — A (инструкция уточнена). Потолок M4 ≈ 97 %, M5 ≈ 93 %.

**Ограничение.** Эталон размечен LLM. Если система будет работать на модели того же семейства, ошибки могут коррелировать. Смягчение: цитаты (метка проверяема), проверка человеком, сравнение провайдеров в ADR-004.

### 7.5 Видимая и отложенная части

- **Единица разбиения — стипендия**, а не запрос: все запросы B и пары A3/A4 про отложенную стипендию уходят в отложенную часть. Иначе — утечка.
- A2: **70 видимых / 30 отложенных**, стратифицированно по странам и типам ловушек. Запросы B, не привязанные к стипендиям (вне домена, несуществующие), — 70/30 случайно по категориям.
- Стипендии, на которых делался спайк (`docs/spike_kt2.md`, 15 страниц), — примеры разработки: только в видимой части, в отложенную не попадают.
- Отложенная часть (30 меток A2, 39 запросов B, 9 пар A4) хранится одним зашифрованным пакетом (`eval/heldout/heldout.enc`), ключ — вне репозитория; в git — sha256 открытого файла (`eval/heldout/SHA256`). **Не открывается до КТ4**; на КТ4 хэш подтверждает, что файл не менялся. В `reference_list.csv` поля `in_profile` и `open_to_ru` отложенных стипендий скрыты (`heldout`).
- **Риск утечки через разработчика.** Разметчик A — тот же агент, что помогает писать код. Правило: метки отложенной части не используются в промптах, few-shot примерах и правилах; промпты и правила отлаживаются только на видимой части.

**Чем eval отличается от данных разработки.** На видимой части отлаживаются промпты и правила; отложенная проверяет обобщение на новых стипендиях и страницах той же стратификации. Примеры спайка — отдельный набор для разработки, в метриках не участвуют.

### 7.6 Процедура прогона

- **Офлайн** (воспроизводимо): извлечение по снимкам A2 → M4, M5, M6, M8(а); запросы B к тетради, собранной из снимков видимой части → M4–M9. **Вживую:** discovery по профилю → M1; ручная проверка выборки найденного → M3.
- **Когда:** smoke — 20 запросов-ловушек (canary) на каждый PR, меняющий промпты или извлечение; полный прогон видимой части — на каждой КТ и перед сменой модели; отложенная часть — только на КТ4.
- **Повторы:** ответы при temperature > 0 — 3 прогона, отчитываемся средним и минимумом; извлечение — 1 прогон + 3 повтора на 20 страницах для оценки разброса.
- **Регрессия:** падение любой метрики >3 п.п. относительно предыдущего прогона или хотя бы одна опасная ошибка на canary — изменение не мержится до полного прогона.
- **Артефакты прогона** сохраняются вместе с метаданными: версия модели, хэш промптов, temperature/seed, версия eval-набора, дата, стоимость, длительность.

## 8. Baseline и план усложнений

### 8.1 Baseline (не LLM)

**B1 «поиск + правила»** — основной baseline, запускается тем же харнессом и на тех же данных, что система:
- discovery: те же запросы в Tavily, топ-10, дедупликация по домену и нормализованному названию; записью считается любой результат с официального домена;
- факты: регулярные выражения по тексту страницы — первая дата рядом со словами `deadline|closing date|apply by`, сумма рядом с `per month|per year|monthly`; статус цикла — по году найденной даты;
- ответы на запросы B — шаблон: найденные ссылки + извлечённые значения;
- конфликты, исправления и память не поддерживаются: по M7 и M9 — честный 0.

Где B1 заведомо ошибётся (видно по спайку): Chevening — выберет 8 July 2027 (дедлайн оффера) вместо дедлайна подачи; Heinrich Böll — дату открытия портала; Lund — 16 February 2026 из прошлого цикла (опасная ошибка); Lund — бюджет программы как сумму. Это и есть то, что должна исправить система.

**B0 «человек с чек-листом»** — ориентир по стоимости и качеству: время и согласие разметки (7.4) дают стоимость одной стипендии вручную и потолок точности. Отдельно не запускается.

### 8.2 План усложнений

Каждый шаг остаётся, только если поднимает свою метрику на видимой части и укладывается в бюджет (3.3). Числа «до → после» записываются в таблицу на КТ3.

| Шаг | Что добавляем | Метрика | Переходим дальше, если |
|---|---|---|---|
| 1 | LLM-извлечение по JSON-схеме с цитатами поверх страниц B1, без тетради | M4, M5, M8 | M4 выше B1 на ≥20 п.п., опасных ≤3 на 100 |
| 2 | discovery в два шага: лиды → официальная страница → подстраницы | M1, M3 | M1 ≥50 % |
| 3 | тетрадь L0–L2, валидатор, статус цикла кодом, политика конфликтов (сравниваем с «все тексты в один промпт с усечением» — бывший baseline v0.1) | M6, M7, M10 | M6 = 100 %, M7 ≥90 % |
| 4 | L3, профиль, память, исправления | M9, M3 | M9 = 100 % |
| 5 | перепроверка по хэшу и планировщик | M11 (телеметрия) | свежесть ≥95 % в рамках бюджета |
| 6 | выбор модели (ADR-004): 2–3 модели на снимках видимой части | M4, M5, M8, стоимость | берём самую дешёвую, которая держит цели M4/M5/M8 |

**Что решили не делать:** дообучение, self-host, собственные парсеры под каждый сайт (LLM-извлечение решает разнородность страниц), подмену User-Agent для обхода блокировок.

## 10. Риски и ограничения (черновик, пополнен на КТ2)

### 10.1 Ограничения модели и чем закрываем

| Ограничение | Чем закрыто |
|---|---|
| даты и арифметика («сколько дней до дедлайна», какой цикл текущий) | текущая дата из инструмента, расчёт в коде |
| факты вне контекста | retrieval по тетради, обязательный источник |
| не знает, чего не знает | статусы `не подтверждено` / `устарел` в контракте, M8 |
| уверенная выдумка значений | цитата обязательна и проверяется кодом на буквальное вхождение в L0 (в спайке 53 / 53) |
| путает тип даты (открытие, оффер, подача) и смысл суммы (бюджет программы) | тип даты в схеме, валидатор, ловушки в eval (в спайке 2 ошибки из 15 страниц) |
| сам ставит статус «подтверждён» без дат | статус вычисляется кодом по датам |
| нет состояния между вызовами | тетрадь + оркестратор |
| длинные агентные циклы | лимит шагов и бюджета на запуск |
| недетерминизм | несколько прогонов eval, агрегирование |

| страница отдаёт 200, но вместо содержания — CAPTCHA или заглушка (найдено при разметке: esteri.it) | средняя (подтверждено) | «факты», извлечённые из текста заглушки | детектор заглушек в валидаторе L0 (ключевые слова CAPTCHA/verification, малая длина), запасной путь через Tavily; CAPTCHA не обходим |
| у большинства стипендий дат цикла 2027/28 ещё нет (61 из 100 на 25.10.2026) | высокая (подтверждено) | система «додумывает» дату по прошлому году | статус «не подтверждено» вычисляется кодом; выдуманный дедлайн — опасная ошибка M4 |
| автоматический обход подстраниц тянет мусор (календари, визы, карьера) | высокая (подтверждено) | лишние токены, ложные даты (академический календарь ≠ дедлайн стипендии) | ранжирование ссылок по ключевым словам + отсев моделью на шаге discovery; тип даты в схеме |
| отложенная часть A2 размечалась до разбиения и есть в ранней истории ветки `kt2` | высокая | формально видна разработчику | хэш фиксирует содержимое; правило «не использовать в промптах и правилах». Решение команды: историю не переписываем — риск принят |
| prompt injection через текст страниц | средняя | искажённые факты | страница — только данные, извлечение строго по JSON-схеме, нет инструментов с побочными эффектами |
| разметка GT дольше плана | средняя | слабый eval к КТ2 | размечает LLM-агент; сначала A1 и видимая часть A2 |
| перерасход бюджета (зацикливание, лишние запуски) | средняя | превышение $25 | лимиты в шлюзе и на запуск, алерт на 80 % |
| провайдер обновил модель | низкая | просадка качества | пиннинг версии, canary eval |
| нет доступа / оплаты API | средняя | блокер разработки | посредник (OpenRouter), запасной провайдер |
| ToS агрегаторов запрещают парсинг | средняя | меньше источников | robots.txt, приоритет официальных сайтов, кэш |
| не хватит времени двум разработчикам | средняя | неполный MVP | Telegram или CLI вместо веб-UI, приоритет ядра тетради |

Опасные непроверенные допущения: доля меняющихся страниц (~15 %), доля стипендий, открытых для граждан РФ.

### 10.3 Безопасность и данные
- **Персональные данные:** профиль (гражданство, направление, GPA, сертификат) хранится у нас. Провайдеру уходят только параметры фильтра, без ФИО и контактов. Согласие пользователей получено. Учитываем 152-ФЗ.
- **Логи:** доступ только у команды; хранятся до конца курса.
- **Действия с последствиями:** нет — агент только читает публичные страницы и пишет в свою базу.
- **Снимки страниц в репозитории:** только текст публичных страниц фондов и вузов, без персональных данных; нужны для воспроизводимости eval.
